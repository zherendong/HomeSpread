# Homescreen Canvas UI — 다중 페이지 편집 화면

이 제품의 존재 이유는 "iPhone에서는 한 번에 한 페이지만 보인다"는 제약을 PC 화면으로 푸는 것이다. UI가 그 가치를 전달하지 못하면 나머지 모든 기술은 무의미하다.

## 설계의 출발점

사용자가 이 앱을 여는 이유는 하나다: **여러 페이지를 한눈에 놓고 옮기고 싶다.** 따라서 첫 화면은 설명이나 설정이 아니라 **전체 페이지가 펼쳐진 캔버스**여야 한다.

세 가지가 항상 동시에 성립해야 한다:

| 요구 | 의미 |
|------|------|
| **한눈에 본다** | 페이지가 8개여도 전체 구조가 한 화면에 들어온다 |
| **바로 옮긴다** | 페이지 간 드래그가 특별한 모드 없이 된다 |
| **무엇이 기기에 반영됐는지 안다** | 편집한 것과 기기에 있는 것을 혼동하지 않는다 |

세 번째가 특히 중요하다. 이 앱에서 편집은 **즉시 기기에 반영되지 않는다.** 사용자가 이것을 오해하면 "옮겼는데 아이폰에는 그대로"라는 최악의 경험이 생긴다.

## 상태의 시각적 구분

`observed`(기기의 실제 상태)와 `desired`(편집 중인 목표 상태)는 항상 공존한다. 화면은 이 둘을 **구분해 보여야 한다.**

| 상태 | 표현 |
|------|------|
| 기기와 일치 | 일반 |
| 편집으로 변경됨 (미적용) | 명확한 시각적 구분 — 테두리, 배지, 색조 |
| 인식 실패 항목 (`Unknown`) | 명확히 구분 + 툴팁으로 사유 설명 |
| 낮은 신뢰도 항목 | 약한 구분 표시 |

**"미적용 변경 N개"를 항상 보이는 곳에 둔다.** 사용자가 편집 후 앱을 닫으려 할 때, 미적용 변경이 있으면 경고한다.

낙관적 UI(드래그 즉시 반영)는 편집감을 위해 필요하지만, 그것이 "기기에 반영됐다"는 착각을 만들면 안 된다. 즉시 반영하되 **미적용임을 표시**하는 것이 답이다.

## 좌표계

이 화면에는 최소 네 개의 좌표계가 있다.

```
캔버스 좌표 (줌·팬 적용)
   ↓
페이지 타일 좌표 (각 페이지의 로컬 위치)
   ↓
그리드 슬롯 (행, 열)
   ↓
기기 물리 픽셀 (제스처 실행용)
```

여기에 Windows의 **디스플레이 배율(125% / 150% / 175%)** 이 겹친다.

### 규칙

- **변환은 한 곳에서만 한다.** 좌표 변환 코드가 여러 곳에 흩어지면 반드시 어긋나고, 그 버그는 "가끔 아이콘이 한 칸 옆에 떨어진다"는 형태로 나타나 재현하기 어렵다
- **타입으로 구분한다.** `CanvasPoint`, `SlotIndex`, `DevicePoint`를 서로 다른 타입으로 두면 혼용이 컴파일 시점에 걸린다. 전부 `(int, int)`로 두면 걸리지 않는다
- **DPI 배율을 처음부터 고려한다.** 나중에 대응하려면 좌표를 다루는 모든 코드를 다시 봐야 한다. 100% 배율에서만 개발하면 배율 문제가 출시 직전에 드러난다
- **다중 모니터**에서 창을 옮기면 배율이 바뀔 수 있다. 배율 변경 이벤트를 처리한다

## 드래그 앤 드롭

### 드롭 전에 검사한다

드롭한 뒤 "여기는 안 됩니다"라고 거부하면 편집이 답답해진다. **드래그 중에 유효한 목적지를 시각적으로 표시**하라.

드래그 중 확인할 것:

- 목표 슬롯이 비어 있는가, 아니면 교체·밀어내기가 일어나는가
- 위젯이면 크기가 들어가는가
- 독이면 용량이 남았는가, 그리고 독이 이 항목 타입을 받는가
- 폴더 위라면 폴더에 넣는 것인가 폴더를 지나는 것인가 (의도 구분이 필요하다)

이 검사는 `homescreen-layout-model`의 제약 검사를 호출한다. **UI가 제약 규칙을 자체 구현하지 마라.** 두 벌의 규칙은 반드시 갈라진다.

### 밀어내기 미리보기

`allowsGaps`가 거짓인 모드에서는 아이콘 하나를 옮기면 여러 개가 따라 움직인다. **이것을 드롭 전에 미리 보여줘야 한다.** 보여주지 않으면 사용자는 드롭 후에야 페이지 전체가 흐트러진 것을 발견한다.

### 페이지 간 드래그

여러 페이지가 동시에 보이는 것이 이 앱의 핵심이므로, 페이지 간 드래그는 **가장 매끄러워야 하는 동작**이다. 캔버스 밖으로 끌어야 하는 자동 스크롤 같은 마찰을 만들지 마라 — 화면에 다 보이는데 스크롤이 필요하면 설계가 잘못된 것이다.

## 실행 취소

**첫날부터 커맨드 객체로 설계한다.** 나중에 추가하려면 편집 로직 전체를 다시 써야 한다.

- 각 편집을 실행/취소 가능한 커맨드로 표현한다
- 되돌리기와 다시 하기를 모두 지원한다
- 연속된 미세 조정은 묶어서 한 번에 되돌린다 (드래그 한 번 = 커맨드 하나)
- **적용 후에는 되돌릴 수 없다.** 적용 전 상태를 저장해두고 "이전 레이아웃으로 되돌리기"를 별도 계획으로 제공하는 것은 가능하지만, 그것은 실행 취소가 아니라 새 적용이다. 사용자에게 이 차이를 명확히 하라

## 적용 흐름의 화면

적용은 몇 분이 걸린다. 그동안 화면이 무엇을 보여주는지가 사용자 신뢰를 좌우한다.

### 드라이런 화면 (적용 전, 생략 불가)

- 총 이동 횟수와 예상 소요 시간
- 무엇이 바뀌는지 요약
- 제외된 항목과 사유 (인식 실패, 설치되지 않은 앱)
- 실행 불가 항목과 사유
- 부분 적용 선택지 (예: 이 페이지만)

### 진행 화면

- 현재 몇 단계 중 몇 번째인지
- 지금 무엇을 옮기고 있는지 (아이콘 이름으로)
- 남은 예상 시간
- **취소 버튼** — 항상 활성. 누르면 안전한 지점에서 멈춘다는 것을 알린다
- 기기를 만지지 말라는 안내

### 완료 화면

- 성공 / 부분 성공 / 중단을 구분해 표시
- 부분 성공이면 **완료된 것과 남은 것을 모두 나열**한다. "실패"라고만 쓰지 마라
- 남은 것을 이어서 진행할 수 있는 경로 제공

## 사용자 언어

**기술 용어를 화면에 노출하지 마라.** usbmuxd, lockdownd, springboardservices, iconState, plist, 번들 ID는 모두 내부 용어다.
번역 표는 코드의 `src/ipsm/device.py` `_TRANSLATIONS` 에 한곳으로 모아 두었다. 새 실패 유형을 만나면 거기에 추가한다 — 분기를 UI 곳곳에 흩뿌리면 어떤 실패가 안내 없이 새는지 알 수 없게 된다.

| 내부 상황 | 사용자에게 |
|----------|-----------|
| 기기 미열거 | "iPhone이 연결되지 않았습니다. USB 케이블을 확인해 주세요." |
| 페어링 미신뢰 | "iPhone 화면에서 '신뢰'를 눌러 주세요." |
| 기기가 잠김 | "iPhone 잠금을 해제한 상태로 두고 다시 시도해 주세요." |
| 신뢰 안 됨 | "iPhone 화면의 '이 컴퓨터를 신뢰하시겠습니까?'에서 '신뢰'를 눌러 주세요." |
| 자동화 서비스 미기동 | "iPhone과 연결을 준비하는 중 문제가 생겼습니다. 다시 시도해 주세요." |
| 추출 부분 실패 | "일부 화면을 읽지 못했습니다. 다시 시도하거나 그대로 진행할 수 있습니다." |

**모든 오류 메시지에 다음 행동을 담아라.** "오류가 발생했습니다"만 있는 메시지는 사용자를 막다른 길에 세운다.

## 빈 상태와 첫 실행

- 기기가 연결되지 않았을 때가 **가장 흔한 첫 화면**이다. 이 화면이 연결 방법을 안내해야 한다
- 사전 준비는 두 가지뿐이다 — Apple Devices(또는 iTunes) 설치, 그리고 iPhone에서 '신뢰'. 개발자 모드·Xcode·탈옥은 필요 없다. 이 사실을 첫 화면에서 알려 주면 사용자의 심리적 장벽이 크게 낮아진다
- 읽기가 몇십 초 걸릴 수 있다. 진행 표시 없이 기다리게 하지 마라

## 접근성과 창

- 키보드만으로 편집 가능한 경로를 제공한다 (선택 → 방향키 이동 → 확정)
- 창 크기 변경에 캔버스가 대응한다. 페이지 수가 많으면 자동으로 축소 배치
- 줌 단계를 제공하되, 기본 줌은 **전체 페이지가 보이는 배율**이다
- 색만으로 상태를 구분하지 마라 (미적용 변경 표시에 색 + 형태를 함께 쓴다)

## UI 계약

UI가 하위 계층에 요구하는 것을 계약으로 고정한다. `interface-contract` 규약에 따라 `_workspace/02_contracts/ui-viewmodel.contract.md`에 기록한다.

최소한 포함할 것:

- 표시용 뷰모델 형식 (레이아웃 + 진단 정보)
- 편집 커맨드의 형식
- 제약 검사 요청/응답
- 적용 진행 이벤트의 형식 (단계 시작, 단계 완료, 단계 실패, 전체 완료)
- 취소 요청의 전달 방식

**진행 이벤트를 계약에 반드시 넣어라.** 이것이 빠지면 진행 화면을 만들 수 없고, 뒤늦게 추가하려면 동기화 엔진의 구조를 바꿔야 한다.
