# 原生应用集成 QA：验证模块边界

## 验证优先级

不同缺陷的代价不同。主屏幕备份提供恢复依据，但不能保证完全撤销 iOS 副作用，也不能保证每次恢复成功。

```text
1. 设备与数据安全：是否可能损坏或丢失用户布局
2. 集成一致性：模块边界是否实际匹配
3. 验收要求：功能是否满足要求
4. 代码质量：可读性与结构
```

时间受限时优先保留前两项；跳过设备安全不能称为完成验证。

## 核心方法：同时读取两端

模块单独看来正确，边界仍可能不一致。

| 生产方 | 消费方 | 比较内容 |
|--------|--------|----------|
| 设备读取或历史提取层 | 布局模型 | 字段、类型、完整性；若启用识别方案，再检查置信度 |
| 布局模型 | 界面 | 位置原点、方向、项目类型、Unknown |
| 布局模型 | 同步层 | 网格信息、约束、原始数据保留 |
| 同步层 | 设备桥接 | 原始 iconState、备份顺序、超时和失败 |
| 同步层 | 界面 | 进度、关闭限制、成功与失败结果 |
| 契约文档 | 两端代码 | 文档与实际行为是否一致 |

不能把“文件存在”当成验证。必须逐项对照字段和调用行为。

## 常见缺陷

| 类型 | 表现 | 检查方法 |
|------|------|----------|
| 坐标混用 | 图标偏移一个位置 | 检查画布、网格和历史设备坐标的转换、原点、方向、单位 |
| 标识符混用 | 操作了错误应用 | 检查是否使用 `displayIdentifier` / 合适的 bundle ID，而非名称或位置冒充身份 |
| 丢弃未知项目 | 内容消失 | 跟踪 Unknown 是否被过滤或当成空位 |
| 未识别字段丢失 | 小组件或新 iOS 内容消失 | 确认写入从原始数据派生，而非按有限模型重建 |
| 跳过校验 | 写入失败却显示成功 | 检查原样写回门槛、写前旧状态检查、写后比较 |
| 忽略不完整读取 | 缺失页面被覆盖 | 确认不完整或不支持的结构不能写入 |
| 缺少进度事件 | 界面看似卡住 | 对照事件发出与订阅 |
| 忽略能力或网格约束 | 某些设备或系统出错 | 核对实际配置来源，避免无依据的版本猜测 |
| 缺失依赖处理 | 首次启动只有底层异常 | 跟踪缺库、版本、权限错误能否形成可执行提示 |
| 绕过备份 | 无恢复依据 | 搜索全部 `set_icon_state` 调用 |
| 跨设备恢复 | 布局应用到错误手机 | 检查设备绑定和备份元数据 |
| 原始快照过期 | 覆盖用户在手机上的新修改 | 修改手机状态后应用旧编辑，确认拒绝写入 |

## 每次必须检查的安全项目

1. 应用编辑前必须经过修改与风险确认，不能存在旁路。
2. 应用编辑要求本会话有效的写入验证标记。普通流程经单独确认的真实原样写回建立；明确确认的同设备恢复若读回比较通过，也可建立。新读取或操作失败必须清除标记。
3. Unknown 的原始内容与位置必须保留；用户确认不能替代对未知结构的支持。
4. 所有实际写入统一经过 `guarded_write`，备份写入或重新读取校验失败必须阻止设备写入。
5. 写入前检查当前布局与编辑基线，拒绝过期编辑；不得将此描述为原子 CAS。
6. 写入后比较丢失、意外移动、内容变化与新增项目；仅忽略明确列出的易变字段。
7. 恢复须验证完整性和设备归属，并在用户另行确认后进行。设备、现状和目标备份通过能力检查时，原样写回校验失败本身不应关闭恢复入口；Duo、小组件和未知布局的拒绝具有更高优先级，不能靠恢复绕过。
8. 应用期间阻止关闭窗口，不能强行终止正在进行的设备写入。
9. 清楚提示 App 资源库应用回填以及备份无法撤销该副作用。
10. 使用假设备测试失败路径；真实设备写入仅在用户明确授权具体操作后执行。

用 `rg` 搜索直接写入调用，不能只相信界面按钮禁用。备份、确认或设备匹配出现可绕过路径，按最高严重级别处理。

原文中的“连续失败阈值”“安全点取消并退出编辑模式”属于历史手势执行循环；只有该方案重新启用时才适用，不应要求当前整体写入加入自动重试。

详细检查表见 `references/checklists.md`。

## 验证方式

### 已有代码

- 运行适合变更的测试；无法执行时说明原因。
- 同时审查边界两端。
- 在无设备环境运行模型、约束、备份和假设备失败测试。
- 真机所需条件未具备或未授权写入时，明确标记未验证，不能推断通过。

### 只有设计文档

- 对照契约和各模块设计。
- 在设计层检查上述缺陷类型，例如坐标原点缺失就是缺陷。
- 对照当前安全项目，区分已实现、计划、历史方案和未验证项。

### 渐进验证

每完成一个模块，就验证它与已经完成的相邻模块。晚发现的接口问题往往需要同时修改两端。

## 缺陷报告模板

```markdown
### [BUG-001] {一句话摘要}

- **严重程度**：最高（设备安全）| 高 | 中 | 低
- **类别**：模块边界 | 安全 | 验收 | 质量
- **位置**：{文件:行} ↔ {文件:行}
- **表现**：用户会看到什么
- **原因**：两端分别作出了什么假设
- **复现**：触发条件
- **建议**：应修改哪一端，以及理由
```

边界缺陷必须指出修复哪一端。契约正确就修复违反契约的一端；契约有问题则先协调修改契约。

## 报告结构

```markdown
## 结果概览：通过 N / 失败 M / 未验证 K

## 设备安全
逐项列出当前安全检查结果。

## 模块边界缺陷
### [BUG-001] ...

## 验收追踪
| REQ ID | 状态 | 证据 |
|--------|------|------|

## 未验证事项与原因
说明哪些内容未验证，以及缺少什么条件。
```

未验证不是失败，但把未验证标成通过就是错误。报告必须区分静态审查、假设备测试、真实只读验证与真实写入验证。
