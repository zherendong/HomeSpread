# Native Integration QA — 경계면 검증

## 검증 우선순위

이 제품에서 결함의 대가는 균일하지 않다. **사용자의 홈화면은 되돌릴 수 없다.**

```
1. 기기 안전성      — 사용자의 홈화면이 망가질 수 있는가
2. 통합 정합성      — 모듈 경계가 실제로 맞물리는가
3. 수용 기준 충족   — 요구사항이 실제로 만족되는가
4. 코드 품질        — 가독성, 구조
```

시간이 부족하면 아래에서부터 자른다. 1번을 건너뛴 검증은 검증이 아니다.

## 핵심 방법: 양쪽 동시 읽기

경계면 결함은 **한쪽만 봐서는 절대 보이지 않는다.** 각 모듈은 그 자체로 완벽해 보이고, 오직 두 코드를 나란히 놓았을 때만 어긋남이 드러난다.

| 생산자 | 소비자 | 무엇을 비교하나 |
|--------|--------|---------------|
| 추출 파이프라인 | 레이아웃 모델 | 필드 이름·타입, 신뢰도 값 집합, 부분 실패 표현 |
| 레이아웃 모델 | UI | 슬롯 원점·방향, 항목 타입 열거, `Unknown` 처리 |
| 레이아웃 모델 | 동기화 엔진 | 프로파일 필드, 능력 플래그, 제약 규칙 |
| 동기화 엔진 | 기기 브리지 | iconState 원본 형식(해석하지 않은 채 전달되는가), 백업 선행 여부, 타임아웃, 실패 표현 |
| 동기화 엔진 | UI | 진행 이벤트, 취소 규약, 부분 성공 결과 |
| 계약 문서 | 양쪽 구현 | 문서가 실제 코드와 일치하는가 |

**"파일이 존재한다"는 검증이 아니다.** 두 파일을 열어 필드를 하나씩 대조한 것만이 검증이다.

## 이 프로젝트의 결함 패턴

일반적인 웹 앱 QA 체크리스트로는 잡히지 않는, 이 도메인 고유의 결함들이다. 검증 시 이것부터 찾아라.

| 패턴 | 증상 | 확인 방법 |
|------|------|----------|
| **좌표계 혼선** | 아이콘이 한 칸 옆에 떨어진다 | 캔버스/슬롯/기기 좌표 변환 지점을 전부 찾아 원점·방향·단위를 대조 |
| **식별자 불일치** | 잘못된 앱이 이동한다 | 번들 ID로 대응시키는지, 표시 이름이나 위치로 대응시키는지 확인 |
| **인식 실패의 조용한 소실** | 사용자 앱이 사라진다 | `Unknown`이 UI까지 도달하는지, 중간에서 필터링되는지 추적 |
| **미해석 요소 유실** | 위젯이나 새 iOS 기능이 편집 후 사라진다 | 쓰기에 넘기는 상태가 원본에서 파생되는지, 우리 모델에서 재구성되는지 |
| **검증 생략** | 실패가 조용히 누적된다 | 적용 루프에 단계 검증이 실제로 있는지, 비교 대상이 `expectedState`인지 |
| **부분 실패 무시** | 읽지 못한 페이지의 아이콘이 밀려난다 | `completeness == partial`일 때 계획 수립이 차단되는지 |
| **진행 이벤트 누락** | 진행 화면이 멈춘 것처럼 보인다 | 엔진이 발행하는 이벤트 목록과 UI가 구독하는 목록을 대조 |
| **능력 플래그 무시** | 특정 기기·iOS에서만 깨진다 | 상위 계층에 iOS 버전 분기가 있는지 검색. 있으면 결함 |
| **외부 도구 부재 미처리** | 첫 실행에서 알 수 없는 오류 | 도구 없음/버전 불일치/권한 부족 경로가 사용자 메시지까지 이어지는지 |
| **백업 우회 경로** | 사고가 났을 때 되돌릴 것이 없다 | `set_icon_state` 호출 지점이 백업 경로 하나뿐인지 |

## 기기 안전성 필수 점검

아래는 **매 검증마다 확인한다.** 하나라도 미충족이면 심각도 최상으로 보고한다.

1. **드라이런을 우회해 적용이 시작되는 경로가 없는가**
2. **파괴적 동작(레이아웃 재설정, 폴더 해체)에 명시적 확인이 있고, 무엇이 사라지는지 열거해 보여주는가**
3. **낮은 신뢰도·`Unknown` 항목이 사용자 확인 없이 계획에 포함되지 않는가**
4. **연속 실패 임계값이 있고 실제로 중단시키는가**
5. **취소가 안전한 지점에서 멈추고 편집 모드를 종료하는가**
6. **쓰기 전에 백업이 반드시 만들어지고, 백업 실패가 쓰기를 막는가** — 이 프로젝트에서 가장 중요한 검증 항목이다. 백업 없이 쓰는 경로가 하나라도 있으면 그 경로에서 사고가 난다. `set_icon_state()` 를 직접 호출하는 곳이 `guarded_write()` 밖에 또 있는지 grep으로 확인하라
7. **원본에서 해석하지 못한 요소가 왕복 후에도 그대로 남는가 (REQ-017)** — 위젯처럼 우리가 모르는 항목을 우리 모델로 재구성해서 쓰면 조용히 사라진다. 항등 왕복 시험의 전후 비교로 확인한다
8. **비교에서 휘발성 필드(iconModDate 등)를 제외하는가** — 제외하지 않으면 정상 동작이 항상 '불일치'로 보고된다

> 확장 체크리스트는 `references/checklists.md` 참조.

## 검증 방식

### 코드가 있을 때

- 실제로 실행해 본다. 실행 불가하면 그 사실을 보고한다
- 경계면은 코드를 나란히 놓고 대조한다
- 기기 없이 검증 가능한 부분(시뮬레이터, 제약 검사, 좌표 변환)은 반드시 실행한다
- 기기가 필요한 부분은 **`미검증`으로 명확히 표시한다.** 추측으로 통과시키지 마라

### 설계 문서만 있을 때

- 계약 문서와 각 모듈의 설계 문서를 대조한다
- 위의 결함 패턴 표를 설계 수준에서 적용한다 — 설계에 이미 좌표계 정의가 없으면 그것이 결함이다
- 안전성 점검 6항목이 설계에 반영되어 있는지 확인한다

### 점진적 검증

전체가 완성된 뒤 한 번 검증하지 마라. **각 모듈이 완성될 때마다 그 모듈과 이미 완성된 이웃의 경계를 검증한다.** 늦게 발견된 경계면 결함은 양쪽 모듈을 모두 고쳐야 한다.

## 결함 보고

```markdown
### [BUG-001] {한 줄 요약}

- **심각도**: 최상(기기 안전성) | 상 | 중 | 하
- **분류**: 경계면 | 안전성 | 수용 기준 | 품질
- **위치**: {파일:줄} ↔ {파일:줄}   ← 경계면 결함은 양쪽을 모두 적는다
- **증상**: 사용자에게 어떻게 나타나는가
- **원인**: 두 쪽이 각각 무엇을 가정하고 있는가
- **재현**: 어떤 상황에서 발생하는가
- **제안**: 어느 쪽을 고치는 것이 맞는가, 그리고 왜
```

**"제안"에 어느 쪽을 고칠지를 쓰라.** 경계면 결함은 양쪽 다 고칠 수 있고, 잘못된 쪽을 고치면 계약이 흔들린다. 계약이 옳으면 계약을 어긴 쪽을, 계약이 부실하면 계약을 고친다.

## 보고서 구조

```markdown
## 요약 — 통과 N / 실패 M / 미검증 K

## 기기 안전성 (심각도 최상)
필수 점검 6항목의 결과

## 경계면 결함
### [BUG-001] ...

## 수용 기준 추적
| REQ ID | 상태 | 근거 |

## 미검증 항목과 사유
무엇을, 왜 검증하지 못했는가
```

**미검증 항목을 반드시 남겨라.** 기기가 없어서, 외부 도구가 없어서 확인하지 못한 것들이 이 프로젝트에는 많다. 이것을 숨기면 리더가 검증되지 않은 부분을 검증된 것으로 오해한다. **미검증은 실패가 아니지만, 미검증을 통과로 표시하는 것은 실패다.**
