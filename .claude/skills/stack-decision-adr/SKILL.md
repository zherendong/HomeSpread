# Stack Decision ADR — 되돌리기 어려운 결정의 기록

## 언제 ADR을 쓰는가

모든 결정이 ADR 대상은 아니다. 기준은 **되돌리는 비용**이다.

| ADR을 쓴다 | 쓰지 않는다 |
|-----------|-----------|
| UI 프레임워크·언어·런타임 선택 | 라이브러리 버전 업 |
| 외부 도구 채택 (라이선스 영향) | 함수 이름·파일 구조 |
| 모듈 경계와 의존 방향 | 내부 구현 방식 |
| 배포·패키징 방식 | 로그 형식 |
| 데이터 저장 형식 | 코드 스타일 |

**나중에 "왜 이렇게 했지?"라고 물을 결정이면 ADR 대상이다.**

## 이 프로젝트의 선택 기준

일반적인 스택 선택과 다른 점이 하나 있다. 이 앱의 어려운 부분은 UI가 아니라 **기기 통신 계층**이다.

따라서 기준의 우선순위는:

1. **기기 통신 계층과의 마찰이 가장 적은가** — usbmuxd/lockdownd 계열 라이브러리, WebDriverAgent 클라이언트가 그 언어·런타임에 존재하는가. 없으면 별도 프로세스를 띄우고 IPC를 만들어야 하며, 그 비용이 UI 편의성의 이득을 넘어선다
2. **Windows 배포가 현실적인가** — 단일 실행 파일 또는 간단한 설치 프로그램으로 배포 가능한가. 런타임 사전 설치를 요구하면 사용자가 이탈한다
3. **드래그 앤 드롭이 있는 밀도 높은 캔버스를 감당하는가** — 수십~수백 개 아이콘, 부드러운 드래그
4. **번들에 외부 실행 파일을 포함할 수 있는가** — 대부분의 기기 통신 경로는 외부 도구를 필요로 한다
5. 개발 속도, 생태계

**UI 편의성을 1번에 두지 마라.** 이 프로젝트에서 가장 흔한 실패 경로는 "UI가 편해서" 고른 스택이 기기 통신 라이브러리를 지원하지 않아, 결국 별도 프로세스 + IPC + 배포 복잡도를 떠안는 것이다.

## ADR 형식

`_workspace/02_desktop-app-architect_adr-{번호}-{주제}.md`

```markdown
# ADR-001: {결정 제목}

**상태**: 제안됨 | 채택됨 | 폐기됨 | ADR-00N으로 대체됨
**날짜**: YYYY-MM-DD
**관련 요구**: REQ-012, REQ-018

## 맥락

이 결정을 하게 만든 상황. 제약 조건. 무엇이 걸려 있는가.
(검증되지 않은 전제가 있으면 [미검증]으로 표기)

## 검토한 대안

### 대안 A: {이름}
- 장점:
- 단점:
- 이 프로젝트에 특히 관련된 점:

### 대안 B: {이름}
...

## 결정

무엇을 선택했는가.

## 근거

왜 그 대안인가. 위 선택 기준 중 어느 것이 결정적이었는가.

## 결과

- 이 결정으로 가능해지는 것:
- 이 결정으로 어려워지는 것:
- 이 결정이 강제하는 후속 결정:

## 재검토 조건

무엇이 사실로 밝혀지면 이 결정을 다시 봐야 하는가.
(예: "WDA 클라이언트를 이 런타임에서 안정적으로 쓸 수 없다고 확인되면")
```

## 작성 원칙

### 대안을 실제로 검토하라

대안이 하나뿐인 ADR은 ADR이 아니라 통보다. 최소 2개, 가급적 3개의 실질적 대안을 검토하고, **각 대안이 왜 탈락했는지**를 쓴다. 탈락 사유가 나중에 재검토의 근거가 된다.

### 재검토 조건을 반드시 쓴다

이 프로젝트에는 `[미검증]` 정보가 많다. 미검증 전제 위에서 결정해야 할 때가 있고, 그것 자체는 문제가 아니다. **문제는 그 전제가 뒤집혔을 때 아무도 결정을 다시 보지 않는 것이다.**

재검토 조건을 명시하면, 검증 결과가 나왔을 때 어떤 ADR을 다시 열어야 하는지 알 수 있다.

### 결정을 바꿀 때는 새 ADR을 쓴다

기존 ADR을 수정하지 마라. 새 ADR을 만들고 기존 것의 상태를 `ADR-00N으로 대체됨`으로 바꾼다.

이유: **왜 처음에 그렇게 결정했는지가 왜 바꿨는지만큼 중요하다.** 원래 근거를 지우면, 몇 달 뒤 누군가 같은 함정에 다시 빠진다.

### 근거는 이 프로젝트의 언어로 쓴다

"성능이 좋다", "생태계가 크다" 같은 일반론은 근거가 아니다. **이 프로젝트의 구체적 제약과 연결하라**: "이 런타임에는 lockdownd 클라이언트 구현이 있어 별도 프로세스가 불필요하다", "단일 exe 배포가 가능해 사용자가 런타임을 설치하지 않아도 된다".

## 의존 방향 ADR

스택 다음으로 중요한 결정이 모듈 간 의존 방향이다. 이 프로젝트에서는 한 방향이 강하게 권장된다:

```
UI  →  동기화 엔진  →  레이아웃 모델
                    ↘  기기 브리지  →  (외부 도구)
```

- **레이아웃 모델은 아무것도 의존하지 않는다.** 순수 데이터 + 제약 규칙. 이래야 테스트할 수 있다
- **기기 브리지가 외부 도구를 감싼다.** 외부 도구의 존재를 다른 계층이 알지 못하게 한다. 도구를 교체할 때 브리지만 바꾸면 되고, 도구가 없는 환경에서도 나머지를 개발·테스트할 수 있다
- **UI는 기기 브리지를 직접 호출하지 않는다.** 호출하기 시작하면 UI에 재시도·타임아웃·연결 상태 처리가 섞여 들어간다

이 방향을 ADR로 고정하고, 위반이 발견되면 결함으로 다룬다.

## 스택 결정 전 반드시 확인할 것

1. 선택 후보 언어·런타임에 iOS 기기 통신 라이브러리가 **실제로 존재하는가** (이름만이 아니라 최근 iOS 버전 지원 여부)
2. 그 라이브러리의 라이선스가 이 앱의 배포 형태와 양립하는가
3. 필요한 외부 실행 파일을 번들에 넣어 배포할 수 있는가
4. 관리자 권한이나 드라이버 설치가 필요한가 — 필요하다면 사용자 안내 부담이 크다
5. 백그라운드 장시간 작업(수 분간의 적용 루프) 중 UI가 응답성을 유지할 수 있는가

**1번과 2번은 `ios-protocol-specialist`의 조사 결과에 의존한다.** 그 결과 없이 스택을 확정하지 마라. 순서를 뒤집으면 스택을 두 번 고르게 된다.
