# 技术栈与架构决策记录

## 何时编写 ADR

依据是改变决定的成本，而不是每件事都要形成 ADR。

| 应记录 | 通常不需要 |
|--------|------------|
| 界面框架、语言、运行时 | 普通依赖版本升级 |
| 有许可影响的外部工具 | 函数名或局部文件组织 |
| 模块边界、依赖方向 | 局部实现方式 |
| 分发与打包方式 | 一般日志格式 |
| 数据存储格式 | 代码风格 |

将来需要追问“为什么这样设计”的重大决定，应留下 ADR。

## 本项目的选择标准

设备通信和布局安全会约束整个应用，不能只根据界面开发便利性选择技术栈。

优先考虑：

1. **与设备协议的集成成本。** 需要的 usbmuxd、lockdownd、SpringBoard 客户端是否适用于所选语言和运行时。当前采用 `pymobiledevice3`；WDA 客户端只属于历史手势研究。缺少原生库会引入子进程、IPC 和分发成本。
2. **目标平台能否可靠分发。** macOS 使用可直接启动的 `.app`；Windows 的可执行目录或安装包属于其平台方案。要求普通用户手工配置运行时会增加使用门槛。
3. **密集画布与拖放能力。** 数十至数百图标需要可读、流畅的交互。
4. **依赖能否随包分发。** 核对库、扩展及确实需要的外部程序，而非假设所有协议都依赖独立可执行工具。
5. 开发效率与生态。

常见失败是先选便于做界面的技术，再发现协议库无法集成，最后承担额外进程和部署复杂度。

## 编写原则

### 实际比较备选方案

至少检查两个实质不同的方案，合适时比较三个；记录未选方案的具体原因。不能虚构比较，也不要为已经明确的局部修复强行制造架构选择。

### 写明复审触发条件

如果必须在不确定前提下作出决定，应标出假设、影响和验证方式。新证据否定假设时，明确哪份 ADR 需要重新审视。涉及设备写入的未验证前提不能被包装成已验证安全能力。

### 改变决定时保留历史

创建新的 ADR，在原记录中注明被哪份新记录替代，保留原理由。语言翻译和事实勘误可以直接修正文档，但应明确历史环境，不能抹去导致旧决定的证据。

### 用具体约束说明理由

“性能更好”“生态更大”不够具体。应写成“该运行时已有所需 lockdownd 客户端，无需额外进程”，或“可将运行时随 `.app` 分发，用户无需另行安装 Python”。

稳定选择直接陈述；只有确有阶段计划时才使用“暂时”“第一版”等措辞。未来工作应有任务或触发条件。

## 依赖方向

```text
界面 → 后台工作线程 / 同步层 → 布局模型
                            ↘ 设备桥接 → 协议库
```

- 布局模型不依赖界面或设备库，数据与约束可在无设备环境测试。基础工具或翻译依赖不等于反向依赖界面。
- 设备桥接集中封装外部协议库。替换库时不应迫使其他模块直接理解它的 API。
- 界面不直接执行设备 I/O，通过工作线程提交操作，避免界面混入重试、超时和连接细节。

记录实际采用的依赖方向，发现违反时作为集成问题处理。

## 确定技术栈前的检查

1. 候选语言或运行时是否确实存在所需协议实现，以及目标 iOS 版本的证据。
2. 许可证是否适合实际分发形式。
3. 所需依赖能否合法、可靠地随包分发。
4. 是否需要管理员权限或驱动，用户操作成本是什么。
5. 连接、图标获取、备份和写后校验期间界面是否保持响应。历史手势方案还需评估数分钟的执行循环。

前两项依赖设备协议调查。当前上游 Python + Qt 的理由记录在已有 ADR 中；macOS 适配应依据新的平台差异评估，而不是自动重做整个技术栈。
