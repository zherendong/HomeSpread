# iOS Device Protocol — Windows에서 비탈옥 iPhone 다루기

Windows PC에서 iPhone의 화면을 읽고 조작하기 위한 통신 계층의 지도와 조사 절차.

## 이 스킬을 쓰는 방식

이 문서는 **정답표가 아니라 지도**다. Apple의 기기 통신 스택은 iOS 메이저 버전마다 바뀌고, 이 분야의 온라인 자료 상당수는 이미 낡았다. 여기 적힌 것은 조사의 출발점이며, 결정의 근거가 되려면 검증을 거쳐야 한다.

## 검증 표기 규약 (필수)

프로토콜에 관한 모든 주장에 다음 중 하나를 붙인다:

| 표기 | 의미 | 사용 조건 |
|------|------|----------|
| `[확인됨]` | 이 프로젝트에서 실제로 재현했다 | 명령어와 출력을 로그에 남겼을 때만 |
| `[문헌]` | 도구 문서·소스·이슈트래커에서 확인 | 출처 URL 또는 저장소 경로 병기 필수 |
| `[미검증]` | 추정 | **이 표기 위에 제품 결정을 세우지 않는다** |

이 규약이 필요한 이유는 명확하다. 낡은 정보로 세운 계획은 구현 단계에서 통째로 무너지고, 그때는 이미 다른 모듈들이 그 계획을 전제로 만들어져 있다. 표기가 붙어 있으면 무엇을 먼저 검증해야 하는지가 자동으로 드러난다.

## 계층 구조

```
[Windows 앱]
     │
     ├─ 연결 계층 ──── usbmuxd (USB 다중화) → lockdownd (인증·서비스 시작)
     │                    ↓
     ├─ 권한 계층 ──── 페어링 레코드 · 개발자 모드 · 개발자 이미지(DDI) · (iOS 17+) 터널
     │                    ↓
     ├─ 서비스 계층 ── 스크린샷 · 앱 목록/설치 · 진단 · 테스트 실행
     │                    ↓
     └─ 자동화 계층 ── WebDriverAgent (접근성 트리 · 제스처 주입)
```

아래로 갈수록 얻는 것이 많아지고 사전 요구사항도 무거워진다. **필요한 최소 깊이가 어디까지인지**를 먼저 정하는 것이 이 조사의 핵심이다.

## 이 제품이 필요로 하는 것

홈화면 레이아웃 관리 앱은 다음 네 가지 능력을 요구한다:

| 능력 | 필요 계층 | 대안 존재 여부 |
|------|----------|--------------|
| 기기 인식·연결 | 연결 | 없음 (필수) |
| 홈화면 **구조** 읽기 (앱 위치·폴더·페이지) | 자동화(권장) 또는 서비스+이미지인식 | 있음 — 아래 "레이아웃 읽기 경로" |
| 홈화면 **모양** 읽기 (스크린샷) | 서비스 또는 자동화 | 있음 |
| 홈화면 **변경** (아이콘 이동) | 자동화 | 사실상 없음 — 아래 "쓰기의 근본 제약" |

**쓰기가 자동화 계층을 요구한다**는 점이 이 제품의 구조를 결정한다. 읽기만 가벼운 경로로 하고 쓰기를 무거운 경로로 하면 사용자는 결국 무거운 사전 준비를 해야 한다. 그러므로 조사 순서는 **쓰기 경로부터**다. 쓰기가 불가능하면 읽기 경로를 아무리 최적화해도 제품이 성립하지 않는다.

## 쓰기의 근본 제약

비탈옥 iOS에는 홈화면 레이아웃을 프로그램으로 써넣는 공개 경로가 없다. 실행 가능한 후보는 셋뿐이며, 각각의 성질이 판이하다.

| 경로 | 성질 | 판단 |
|------|------|------|
| **`setIconState` (springboardservices)** | 레이아웃 전체를 plist 하나로 덮어쓴다. 사전 요구사항은 페어링뿐 | **기본 경로 `[확인됨]`** — 다른 경로를 검토하기 전에 이것부터 시험한다 |
| **제스처 재생 (WDA/XCUITest)** | 사람이 하는 동작을 그대로 재생. 느리고 불안정 | **폴백 전용** — `setIconState` 가 거부될 때만 |
| **감독 모드 + 홈화면 레이아웃 구성 프로파일** | 레이아웃을 통째로 지정 가능하나 감독 모드 전환이 기기 초기화를 요구하고 설정 도구가 macOS 중심 | 일반 소비자에게 비현실적. 기업/키오스크 시나리오에서만 검토 |
| **가이드 모드 (사용자가 직접 수행)** | 앱이 다음 동작을 안내하고 사람이 옮김 | 자동화 계층 불필요. **자동 경로의 필수 보험** |

가이드 모드를 부가 기능으로 보지 마라. 제스처 재생 경로는 Apple의 UI 변경 한 번으로 깨질 수 있고, 사전 요구사항(개발자 모드·서명)의 마찰을 감당하지 못하는 사용자가 있다. 계획 엔진은 두 모드에서 동일하게 쓰이므로, 가이드 모드는 추가 비용이 작고 보험 가치가 크다.

> 제스처 원시 동작의 구체적 형태와 홈화면 편집 모드의 특성은 `layout-diff-planner` 스킬이 다룬다. 이 스킬은 그 제스처를 **어떤 채널로 전달하는가**까지를 담당한다.

## 레이아웃 읽기 경로

| 경로 | 얻는 것 | 사전 요구 | 정확도 | 비고 |
|------|--------|----------|-------|------|
| **접근성 트리 덤프 (WDA)** | 아이콘 라벨 + 좌표를 **구조화된 데이터**로 | 자동화 계층 전체 | 높음 | 1차 경로 권장 |
| **스크린샷 + 이미지 인식** | 픽셀. 그리드 좌표는 계산, 앱 식별은 매칭/OCR | 스크린샷 서비스 또는 WDA | 중간 | 보조·교차 검증용 |
| **설치 앱 목록** | 번들 ID·표시 이름·아이콘 이미지 | 서비스 계층 | 높음 | **식별의 정답지**. 위 두 경로와 반드시 결합 |
| **백업 파싱** | 이론상 SpringBoard 상태 | 백업 생성(느림) + 암호화 시 복호화 | 불명 | `[미검증]` — 최신 iOS에서 유효한지 확인 필요 |

**세 번째 경로를 반드시 결합하라.** 접근성 라벨이나 OCR로 얻는 것은 *표시 이름*이지 앱의 정체가 아니다. 표시 이름은 지역화되고, 사용자가 바꿀 수 있고, 서로 다른 앱이 같은 이름을 가질 수 있다. 설치 앱 목록에서 얻는 번들 ID만이 안정적인 키다.

> 각 경로의 상세 절차와 결과 형태는 `references/capture-and-structure.md` 참조.

## 조사 순서

이 순서를 지켜라. 뒤집으면 나중 단계에서 앞 단계 결과를 버리게 된다.

1. **쓰기 경로 타당성** — `setIconState` 가 대상 기기·iOS 버전에서 실제로 적용되는가. **항등 왕복 시험(읽은 그대로 다시 쓰고 재확인)으로 판정한다.** 성립하지 않으면 제품 범위를 근본적으로 재검토해야 하므로 가장 먼저 답한다. 이 시험을 통과하기 전에는 어떤 변경도 기기에 쓰지 않는다
2. **사전 요구사항의 사용자 마찰** — 개발자 모드, 서명, 재설치 주기, 관리자 권한. 이것이 제품의 실질적 대상 사용자를 결정한다
3. **연결 계층 확보** — Windows에서 기기 열거·페어링이 실제로 되는가
4. **읽기 경로 선택** — 쓰기 경로가 자동화 계층을 이미 요구한다면 읽기도 같은 계층을 쓰는 것이 합리적이다
5. **도구 선정** — 위 결정을 만족하는 오픈소스 도구를 고르고 라이선스를 확인

## 도구 조사 체크리스트

바닥부터 구현하기 전에 기존 도구를 조사한다. 이 영역은 리버스 엔지니어링 난이도가 높아 직접 구현의 비용이 크다.

각 후보에 대해 확인할 것:

- [ ] **Windows 네이티브 지원** — WSL/VM 요구는 소비자 배포에서 사실상 탈락 사유
- [ ] **최신 iOS 대응 상태** — 이슈트래커에서 최근 iOS 버전 키워드로 검색. 미해결 이슈가 쌓여 있으면 위험 신호
- [ ] **라이선스** — GPL/LGPL 계열이면 배포 형태에 따라 의무가 발생한다. **반드시 보고할 것**
- [ ] **재배포 가능성** — Apple이 배포하는 구성요소는 재배포할 수 없다. 사용자 설치 안내로 우회해야 하는지 확인
- [ ] **관리자 권한·드라이버 요구** — 설치 경험과 기업 환경 사용 가능성에 직결
- [ ] **유지 활성도** — 최근 커밋, 릴리스 주기. 이 분야에서 방치된 도구는 다음 iOS에서 깨진다
- [ ] **호출 형태** — 실행 파일인가 라이브러리인가. 아키텍처(프로세스 분리 여부)에 영향

조사 대상 도구군과 각각의 성격은 `references/tooling.md` 참조.

## 연결 문제 진단

"연결 실패"는 진단이 아니다. 실패 지점을 다음 단계 중 하나로 특정하라 — 각 단계마다 원인과 해결이 전혀 다르다.

1. **USB 열거 실패** — 기기가 시스템에 나타나지 않음. 케이블·포트·드라이버 문제
2. **usbmuxd 인식 실패** — 다중화 데몬이 기기를 목록에 올리지 못함. 서비스 미실행 또는 충돌
3. **페어링/신뢰 실패** — 기기 화면의 "이 컴퓨터를 신뢰하시겠습니까?" 미승인, 또는 기기 잠금 상태
4. **서비스 시작 실패** — 페어링은 됐으나 특정 서비스를 열 수 없음. 개발자 이미지 미마운트 또는 iOS 버전 요구사항 미충족
5. **자동화 계층 실패** — 서비스는 열리나 WDA가 실행/응답하지 않음. 서명 만료, 앱 미설치, 포트 포워딩 문제

각 단계의 확인 방법과 흔한 원인은 `references/connection-troubleshooting.md` 참조.

## 사용자에게 노출할 오류 메시지

이 계층의 오류는 원문 그대로 사용자에게 보이면 안 된다. 진단 결과를 **사용자가 취할 수 있는 행동**으로 번역하라.

| 내부 실패 | 사용자에게 보일 문구 |
|----------|-------------------|
| USB 열거 실패 | "iPhone이 인식되지 않습니다. 케이블을 다시 연결해 주세요." |
| 신뢰 미승인 | "iPhone 화면에서 '신뢰'를 눌러 주세요. 기기 잠금을 먼저 해제해야 합니다." |
| 개발자 모드 꺼짐 | "iPhone 설정 > 개인정보 보호 및 보안 > 개발자 모드를 켜 주세요." (경로는 iOS 버전에 맞춰 확인) |
| 서명 만료 | "기기 연동 구성 요소를 다시 설치해야 합니다." + 재설치 버튼 |

원문 오류는 상세 보기나 로그 파일에 둔다. 삭제하지는 마라 — 지원 요청 시 유일한 단서다.

## 법적·정책 고려

- **상호운용 목적의 프로토콜 분석**과 **암호화 보호 우회**는 법적으로 다르게 취급된다. 후자에 해당할 수 있는 구현(특히 콘텐츠 보호가 걸린 스트리밍 경로)은 도입 전에 반드시 별도 검토를 요청하라
- Apple이 배포하는 바이너리 구성요소는 재배포하지 않는다. 사용자가 직접 설치하도록 안내하거나, 오픈소스 대체 구현을 사용한다
- 제품명·아이콘·마케팅 문구에서 Apple 상표를 사용할 때의 제약을 확인한다
- 의존 오픈소스의 라이선스 의무(소스 공개, 고지, 정적/동적 링크 구분)를 배포 형태 확정 전에 정리한다

이 항목들은 발견 시 **즉시** 보고한다. 배포 직전에 드러나면 되돌릴 수 없다.

## 검증 로그 남기기

검증한 것은 반드시 재현 가능한 형태로 남긴다. 남기지 않으면 다음 세션에서 같은 조사를 처음부터 반복하게 된다.

```markdown
### [확인됨] setIconState 의 실제 동작 (iPhone 14, iOS 26.1 · 2026-08-19)

항등 왕복(읽은 그대로 되쓰기)을 실기기에서 수행한 결과:

| 관측 | 결과 |
|------|------|
| 전송한 것 | 읽은 원본과 바이트 단위로 동일 |
| 보존 | 309개 항목 전부. 순서·폴더 내용·`iconModDate` 까지 동일 |
| 손실 | **없음** |
| 이동 | **없음** |
| 추가 | 4개 — 마지막 페이지 끝에 덧붙음 |
| 소요 | 쓰기 820ms · 되읽기 100ms |

**iOS 는 받은 배치에 없는 '설치된 앱'을 마지막 페이지 끝에 되붙인다.** 앱 라이브러리에만 두었던 앱(홈화면에서 제거한 앱)이 이 경우에 해당한다. 우리가 빠뜨린 것이 아니라 iOS 의 동작이며, `setIconState` 에는 "설치되어 있으나 홈화면에 없음"을 표현할 방법이 없다.

한 번 붙고 나면 모든 설치 앱이 배치된 상태가 되므로 이후 쓰기에서는 더 늘지 않는다. 사용자가 다시 앱 라이브러리로 숨기면, 그 다음 쓰기에서 또 붙는다. **되돌릴 수 없는 것은 아니지만 백업으로 되돌려지지도 않는다** — 백업 복원 역시 쓰기이므로 같은 일이 일어난다. 사용자에게 미리 알려야 하는 유일한 비가역 부작용이다.

따라서 왕복 시험의 합격 기준은 "완전 동일"이 아니라 **"사라진 것도 움직인 것도 없다"** 이다. 추가는 눈에 보이고 사용자가 되돌릴 수 있지만, 손실과 이동은 그렇지 않다. 이 둘을 뭉뚱그리면 멀쩡한 기기를 위험하다고 판정하거나 그 반대가 된다.
  ```
