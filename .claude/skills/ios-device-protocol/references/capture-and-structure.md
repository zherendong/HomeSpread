## 1. 세 갈래를 결합해야 하는 이유

| 갈래 | 주는 것 | 못 주는 것 |
|------|--------|-----------|
| 접근성 요소 트리 | 위치·표시 이름·계층 구조 | 앱의 정체(번들 ID), 아이콘 이미지 |
| 스크린샷 | 픽셀, 사용자에게 보여줄 화면 | 구조, 폴더 내부, 앱 정체 |
| 설치 앱 목록 | 번들 ID·표시 이름·아이콘 이미지 | 홈화면 어디에 있는지 |

어느 하나로는 완결되지 않는다. 구조는 트리에서, 정체는 앱 목록에서, 사용자에게 보여줄 그림은 스크린샷에서 온다. 셋을 **번들 ID를 축으로** 결합하는 것이 추출 파이프라인의 본질이다.

## 2. 구조 읽기 — 접근성 요소 트리

### 원리

UI 테스트 프레임워크는 화면의 요소를 계층 트리로 노출한다. 홈화면이 전면에 있을 때 이 트리를 덤프하면, 각 아이콘이 **표시 이름(label)과 화면 좌표(rect)** 를 가진 요소로 나타난다.

이것이 이미지 인식보다 우선하는 이유는 단순하다. 픽셀에서 그리드를 역산하는 것보다, 이미 구조화된 데이터를 파싱하는 편이 훨씬 정확하고 기기 모델 차이에 강하다.

### 설계 시 확인할 것

- 홈화면(시스템 런처)의 요소가 실제로 노출되는가. 일반 앱과 시스템 런처의 접근성 노출은 다를 수 있다 — **이것이 이 경로의 첫 번째 검증 항목이다**
- 요소 타입 이름이 iOS 버전에 따라 달라지는가. 타입 문자열에 하드코딩 의존하면 버전 업에서 깨진다
- **폴더**가 어떻게 나타나는가. 닫힌 폴더는 하나의 요소일 것이고, 내부를 읽으려면 열어야 한다 (열기 = 탭 = 상태 변경)
- **독(Dock)** 이 별도 컨테이너로 구분되는가, 아니면 좌표로 판별해야 하는가
- **위젯**이 어떤 형태로 나타나는가. 라벨이 없거나 불명확할 가능성이 높다 — 인식 실패 처리가 필요한 지점
- **검색/App Library** 화면이 별도로 잡히는가
- 화면 밖(다음 페이지)의 요소가 트리에 포함되는가. 포함된다면 페이지 순회가 불필요할 수도 있다

### 파싱 원칙

- **좌표로 그리드 슬롯을 역산한다.** 요소의 rect 중심점을 기기 프로파일의 그리드에 매핑한다. 이때 아이콘 라벨 텍스트가 아니라 아이콘 이미지 영역 기준으로 계산해야 행 판정이 어긋나지 않는다
- **트리 순서를 신뢰하지 마라.** 시각적 순서와 트리 순서가 일치한다는 보장이 없다. 좌표 기준으로 정렬한다
- **알 수 없는 요소를 버리지 마라.** 해석하지 못한 요소는 `unresolved`로 표시하여 모델에 넣는다. 조용히 버리면 그 자리가 빈칸으로 보이고, 나중에 다른 아이콘이 그 자리로 이동하게 계획된다

## 3. 모양 읽기 — 스크린샷

### 용도

1. **사용자에게 보여주는 그림** — PC 화면의 각 페이지 타일
2. **구조 읽기의 교차 검증** — 트리에서 읽은 아이콘 수와 스크린샷에서 센 아이콘 수가 다르면 경보
3. **트리 경로가 막혔을 때의 폴백** — 정확도는 낮지만 아무것도 못 하는 것보다 낫다

### 획득 경로

스크린샷은 서비스 계층에서도, 자동화 계층에서도 얻을 수 있다. 어느 쪽을 쓸지는 **이미 확보한 계층**에 따른다. 쓰기를 위해 자동화 계층이 이미 필요하다면 스크린샷도 같은 채널을 쓰는 것이 단순하다.

### 이미지 기반 아이콘 식별 (폴백)

정확도 순서로:

1. **아이콘 이미지 매칭** — 설치 앱 목록에서 얻은 아이콘 이미지와 스크린샷의 crop을 비교. 아이콘 이미지를 얻을 수 있다면 가장 정확하다
2. **라벨 OCR** — 아이콘 아래 텍스트를 읽는다. 지역화·잘림·테마 대비에 취약
3. **위치만 인식** — 무언가 있다는 것만 알고 정체는 미상. `unresolved`로 표시

주의: 사용자가 아이콘 테마(다크/틴트 등)를 적용했으면 아이콘 이미지 매칭이 실패할 수 있다. 매칭 실패를 "빈칸"이 아니라 "미상"으로 처리하는 것이 결정적으로 중요하다.

## 4. 정체 확인 — 설치 앱 목록

### 왜 필수인가

표시 이름은 키가 될 수 없다:
- 지역화된다 (같은 앱이 언어 설정에 따라 다른 이름)
- 서로 다른 앱이 같은 이름을 가질 수 있다
- 앱 업데이트로 바뀔 수 있다

번들 ID만이 안정적이다. 그리고 번들 ID는 **설치 앱 목록에서만** 얻을 수 있다.

### 결합 절차

1. 설치 앱 목록을 조회하여 `{번들 ID → 표시 이름, 아이콘 이미지}` 사전을 만든다
2. 트리에서 읽은 각 아이콘의 표시 이름으로 사전을 조회한다
3. **유일하게 매칭되면** 번들 ID 확정, 신뢰도 높음
4. **여러 개 매칭되면** 아이콘 이미지 비교로 좁힌다
5. **매칭되지 않으면** — 시스템 앱이거나, 폴더거나, 위젯이거나, 사용자가 이름을 바꾼 항목이다. `unresolved`로 표시하고 사용자 확인 대상으로 넘긴다

시스템 내장 앱이 목록에 포함되지 않을 수 있다. 이 경우를 위한 별도 처리(내장 앱 사전)가 필요한지 확인하라.

## 5. 페이지 순회 절차

모든 페이지를 읽으려면 페이지를 넘겨가며 반복해야 한다. 순회는 **상태를 바꾸는 동작**이므로 규율이 필요하다.

### 절차

1. 홈화면 첫 페이지로 정규화한다 (현재 어느 페이지인지 모르는 상태로 시작하지 않는다)
2. 총 페이지 수를 확인한다 (페이지 인디케이터 요소 또는 스와이프 종료 조건)
3. 각 페이지에서: 트리 덤프 + 스크린샷 획득
4. 다음 페이지로 스와이프. **스와이프 후 애니메이션이 끝날 때까지 대기**한 뒤 읽는다
5. 마지막 페이지 도달을 판정한다 — 스와이프해도 내용이 바뀌지 않거나 App Library로 넘어감

### 함정

- **애니메이션 중 덤프**: 전환 중에 읽으면 두 페이지가 섞이거나 좌표가 어긋난다. 안정화 대기 또는 연속 2회 동일 결과 확인
- **페이지 수 오판**: 숨겨진 페이지, App Library, 오늘 보기(위젯 페이지)를 홈화면 페이지로 오인
- **순회 중 상태 변경**: 실수로 아이콘을 눌러 앱이 실행되거나 편집 모드에 진입. 스와이프 시작점을 아이콘이 없는 영역으로 잡는다
- **읽기 도중 실패**: 3페이지까지 읽고 실패했다면 그 3페이지는 유효하다. 전체를 버리지 말고 부분 결과 + 실패 지점을 반환한다

## 6. 결합과 신뢰도 산출

추출 결과의 각 요소에 신뢰도를 부여한다. 이 신뢰도는 UI 표시와 **적용 계획 포함 여부**를 결정하므로 형식적으로 붙여서는 안 된다.

| 신뢰도 | 조건 | 하위 계층의 처리 |
|-------|------|----------------|
| 높음 | 트리 좌표 확보 + 번들 ID 유일 매칭 + 스크린샷 교차 확인 일치 | 정상 편집·적용 대상 |
| 중간 | 트리 좌표 확보 + 번들 ID 매칭, 교차 확인 미수행 | 편집 가능, UI에 약한 표시 |
| 낮음 | 좌표는 있으나 정체 미상 (`unresolved`) | UI에 명확히 표시, **사용자 확인 없이는 이동 계획에 포함하지 않는다** |
| 없음 | 요소를 읽지 못함 | 빈칸으로 처리하지 말 것. "읽지 못한 영역"으로 표시 |

**"읽지 못함"과 "비어 있음"을 절대 같게 취급하지 마라.** 이 둘을 혼동하면 읽지 못한 자리에 다른 아이콘을 옮기는 계획이 세워지고, 실제 기기에서는 그 자리에 있던 앱이 밀려난다. 사용자는 앱이 사라졌다고 느낀다.

### 교차 검증 항목

- 트리에서 센 아이콘 수 vs 스크린샷에서 인식한 아이콘 수
- 페이지 수 vs 페이지 인디케이터가 표시한 수
- 번들 ID 매칭률 (낮으면 앱 목록 조회 실패를 의심)
- 그리드 슬롯 충돌 (두 요소가 같은 슬롯으로 계산되면 좌표 매핑 또는 기기 프로파일이 틀렸다)

마지막 항목이 특히 중요하다. 슬롯 충돌은 기기 프로파일(행×열)이 실제와 다르다는 가장 확실한 신호다.
