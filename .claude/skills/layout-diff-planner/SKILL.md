# Layout Diff Planner — 적용 계획과 실행 (폴백 경로)

> **⚠ 먼저 읽어라 — 이 스킬은 기본 경로가 아니다.**
>
> 2026-08-19 조사에서 비탈옥 iPhone에도 홈화면을 쓰는 경로가 있다는 것이 확인되었다:
> `com.apple.springboardservices` 의 `setIconState`. 레이아웃 전체를 plist 하나로 쓴다.
> 제스처 재생, 밀어내기 시뮬레이션, 체크포인트/재개는 **전부 불필요해졌다.**
>
> 기본 경로는 `homescreen-layout-model` + `ios-device-protocol` 이다. 그쪽을 써라.
>
> **이 스킬을 여는 조건은 하나뿐이다:** 항등 왕복 안전 시험(REQ-003)이 실패했거나,
> 대상 기기·iOS 버전이 `setIconState` 를 거부해서 쓰기 경로가 성립하지 않을 때.
> 그때 되돌아올 곳이 있어야 하므로 이 문서를 보존한다.
>
> 아래 내용은 그 조건이 성립할 때만 유효하다.

목표 레이아웃을 실제 기기에 반영하기 위한 계획 수립과 안전한 실행.

## 이 문제의 성질 (폴백 상황 전제)

`setIconState` 를 쓸 수 없는 상황이라면, 홈화면 레이아웃을 써넣을 API가 없다. 유일하게 실행 가능한 경로는 **사람이 하는 동작을 그대로 재생하는 것**이다. 여기서 세 가지 성질이 따라 나오고, 이 스킬의 모든 지침이 이 셋에서 파생된다.

| 성질 | 결과 | 대응 |
|------|------|------|
| **느리다** | 이동 횟수 = 사용자 대기 시간 | 이동 횟수 최소화가 제품 가치의 핵심 |
| **불안정하다** | 실패가 조용히 일어난다. 잘못 떨어진 아이콘도 오류를 내지 않는다 | 매 단계 검증 |
| **되돌릴 수 없다** | 트랜잭션이 없다. 중간에 멈추면 어느 상태도 아니다 | 체크포인트 + 중단 안전성 |

## 진행 순서

1. **비용 함수 정의** — 측정된 수치로. 추정치로 채우지 않는다
2. **밀어내기 모델 확립** — 이것이 없으면 계획한 횟수와 실제 횟수가 다르다
3. **diff 계산** — 모델 연산 목록으로
4. **계획 수립** — 연산을 실행 가능한 최소 비용 순서로
5. **드라이런** — 사용자에게 이동 횟수와 예상 시간 제시
6. **실행·검증 루프**
7. **완료 또는 중단 보고**

## 1. 비용 함수

이동 1회의 비용은 균일하지 않다.

| 연산 | 상대 비용 요인 |
|------|--------------|
| 같은 페이지 내 이동 | 기본 |
| 인접 페이지로 이동 | 기본 + 페이지 전환 대기 |
| 먼 페이지로 이동 | 기본 + 전환 횟수 × 대기 |
| 폴더에 넣기 | 기본 + 폴더 애니메이션 |
| 폴더에서 꺼내기 | 폴더 열기 + 드래그 + 닫기 |
| 폴더 해체 | **내부 아이콘 수 × 꺼내기** |
| 폴더 생성 | 기본 + 폴더 생성 애니메이션 + (이름 지정 시 추가) |
| 페이지 재정렬 | 별도 편집 화면 진입 필요 여부에 따라 다름 |

**수치는 `ios-protocol-specialist`가 실제 기기에서 측정한 값을 쓴다.** 측정치가 없으면 요청하라. 임의의 상수로 비용 함수를 채우면 드라이런의 예상 시간이 틀리고, 사용자에게 한 약속이 깨진다.

비용 함수에는 **실패 확률**도 들어간다. 먼 페이지로의 드래그는 실패율이 높을 수 있다. 실패는 재시도 비용이므로 기대 비용에 반영한다.

## 2. 밀어내기 모델 — 계획의 전제

이것을 모델링하지 않으면 계획이 무의미해진다.

`allowsGaps`가 **거짓**인 모드에서 레이아웃은 순서 있는 리스트다. 아이콘 하나를 앞쪽 슬롯으로 옮기면 그 사이의 모든 아이콘이 한 칸씩 뒤로 밀리고, 밀림은 **페이지 경계를 넘어 전파된다.** 페이지가 꽉 차 있으면 마지막 아이콘이 다음 페이지로 넘어간다.

그래서 순진한 계획 — "목표 배치를 슬롯 순서대로 하나씩 실행" — 은 다음과 같이 실패한다:

1. A를 목표 위치로 옮긴다
2. 밀어내기로 B, C, D가 각각 한 칸씩 이동한다
3. 다음 단계에서 B를 목표 위치로 옮긴다
4. 다시 밀어내기가 일어나 A가 움직인다
5. 이전 작업이 무효가 된다

**계획 엔진은 각 이동 후의 상태를 밀어내기 규칙에 따라 시뮬레이션해야 한다.** 시뮬레이션 없이 세운 계획은 실행 중 검증에서 계속 어긋나고, 재계획이 반복되어 실제 소요 시간이 예상의 몇 배가 된다.

`allowsGaps`가 **참**인 모드에서는 이 문제가 없다. 대신 빈칸을 만들고 없애는 것 자체가 의미 있는 연산이 된다.

> 밀어내기 규칙의 구체적 형태(전파 방향, 페이지 넘김 조건)는 대상 iOS 버전에서 **실측으로 확인**한다. 상세 절차는 `references/reflow-and-gestures.md` 참조.

## 3. diff 계산

`observed`와 `desired`를 비교해 모델 연산 목록을 만든다.

### 원칙

- **번들 ID로 대응시킨다.** 슬롯 위치로 대응시키면 "옮긴 것"과 "빼고 넣은 것"을 구분하지 못한다
- **낮은 신뢰도 항목과 `Unknown`은 diff에서 제외한다.** 사용자가 명시적으로 확인한 경우에만 포함
- **`observed.completeness`가 `partial`이면 계획을 세우지 않는다.** 읽지 못한 영역이 있는 상태에서 이동하면 그 영역의 아이콘이 밀려난다
- 삭제·설치는 이 앱의 범위가 아니다. `desired`에 있는데 기기에 설치되지 않은 앱은 연산이 아니라 **경고**로 보고한다

### 연산 종류

```
Move        : 항목을 다른 슬롯/페이지로
MoveToDock  : 독으로 (독은 별도 컨테이너)
IntoFolder  : 폴더 안으로
OutOfFolder : 폴더 밖으로
CreateFolder: 두 아이콘을 겹쳐 새 폴더
RenameFolder: 폴더 이름 변경
ReorderPage : 페이지 순서 변경
```

각 연산에 **선행 조건**이 있다. 예를 들어 꽉 찬 페이지에 넣으려면 먼저 자리를 비워야 한다. 선행 조건을 무시한 연산 목록은 실행 순서를 정할 수 없다.

## 4. 계획 수립

### 목표

최소 비용 순서를 찾는 것. 완전 최적해는 조합 폭발이 일어나므로, **충분히 좋은 해를 빠르게** 찾는 접근이 현실적이다.

### 도구

| 기법 | 언제 유용한가 |
|------|-------------|
| **임시 슬롯(스크래치)** | 마지막 페이지의 빈 공간을 작업 공간으로 써서 순환 의존을 끊는다 |
| **페이지별 분할** | 페이지 내부에서 완결되는 이동을 먼저 처리해 페이지 전환 횟수를 줄인다 |
| **역순 배치** | 밀어내기 모드에서는 뒤쪽부터 채우면 밀림 전파가 줄어들 수 있다 |
| **일괄 페이지 방문** | 같은 페이지에서 처리할 연산을 모아 전환 비용을 분산 |

**순환 의존**에 주의하라. A의 자리에 B가 가야 하고 B의 자리에 A가 가야 하면, 하나를 임시 슬롯으로 빼야 한다. 임시 슬롯이 없으면(모든 페이지가 꽉 참) 새 페이지를 만들거나, 계획이 불가능함을 보고한다.

### 계획 결과 형식

```
Plan
  steps[]
    index         : 순번
    operation     : 연산
    from / to     : 위치
    expectedState : 이 단계 후의 예상 레이아웃 (검증 기준)
    estimatedMs   : 예상 소요
    riskLevel     : 실패 가능성
  totalSteps      : 총 이동 횟수
  estimatedTotal  : 총 예상 시간
  warnings[]      : 설치되지 않은 앱, 제외된 저신뢰 항목 등
  infeasible[]    : 실행 불가 연산과 사유
```

`expectedState`를 반드시 포함하라. 검증 단계가 무엇과 비교할지가 여기서 나온다.

## 5. 드라이런

**적용 전에 사용자에게 반드시 보여준다.**

- 총 이동 횟수
- 예상 소요 시간 (범위로. "약 4~7분")
- 제외된 항목과 사유
- 실행 불가 연산과 사유
- 파괴적 동작이 포함되어 있으면 그 목록

사용자가 이 화면에서 "이건 너무 오래 걸리니 이 페이지만 적용하겠다"고 판단할 수 있어야 한다. 그래서 **부분 적용을 위한 계획 분할**을 지원한다.

드라이런 없이 적용이 시작될 수 있는 경로를 만들지 마라. 이 제품에서 가장 위험한 UX 결함이다.

## 6. 실행·검증 루프

```
각 단계에 대해:
  1. 제스처 시퀀스로 번역
  2. 실행
  3. 안정화 대기
  4. 실제 상태 읽기 (경량 추출)
  5. expectedState와 비교
     ├─ 일치 → 체크포인트 기록, 다음 단계
     └─ 불일치 → 재계획 (현재 실제 상태 기준)
```

### 검증을 생략하지 않는 이유

검증은 비용이다. 하지만 검증 없이 20단계를 실행한 뒤 3단계에서 어긋났음을 발견하면, 그 17단계가 통째로 낭비되고 기기는 예상 못한 상태가 된다. **검증 비용은 재작업 비용보다 항상 싸다.**

검증 주기를 조정 가능하게 하되 기본값은 매 단계로 둔다.

### 어긋남을 발견했을 때

**재계획하라. 예상 상태를 가정하고 계속 진행하는 것이 가장 위험하다.** 어긋난 상태 위에 세운 이후 단계는 전부 엉뚱한 곳을 건드린다.

재계획은 현재의 실제 상태를 새 `observed`로 삼아 diff부터 다시 계산하는 것이다.

## 7. 안전성 규약

이 절의 항목은 협상 대상이 아니다. 사용자의 홈화면은 되돌릴 수 없다.

- **연속 실패 임계값** — 예: 3회 연속 실패 시 중단하고 보고. 무한 재시도로 기기를 휘젓지 않는다
- **사용자 취소** — 현재 제스처를 완료한 뒤 안전한 상태(편집 모드 종료)에서 멈춘다. 드래그 도중 멈추지 않는다
- **체크포인트** — 각 단계 완료 시 진행 지점을 기록. 중단 후 재개할 수 있어야 한다
- **부분 성공 보고** — "30개 중 22개 완료, 남은 8개는 다음과 같습니다". 부분 성공을 실패로 표시하지 마라
- **파괴적 동작 격리** — 레이아웃 재설정, 폴더 해체 등은 명시적 경고 + 이중 확인 뒤에만. 무엇이 사라지는지 정확히 열거해 보여준다
- **저신뢰 항목 제외** — 사용자 확인 없이 `Unknown`이나 저신뢰 항목을 이동하지 않는다

## 8. 가이드 모드

같은 계획을 **사람이 실행**하는 모드. 앱은 다음에 옮길 아이콘과 목적지를 하나씩 안내하고, 사용자가 옮긴 뒤 확인을 누르면 다음으로 넘어간다.

부가 기능이 아니라 **보험이다**:

- 제스처 자동화 경로는 Apple의 UI 변경 한 번으로 깨질 수 있다
- 사전 요구사항(개발자 모드·서명)의 마찰을 감당하지 못하는 사용자가 있다
- 자동화보다 사용자가 직접 하는 편이 빠른 경우도 있다 (작은 변경)

계획 엔진은 두 모드에서 동일하다. 다른 것은 실행 주체와 검증 방식(자동 읽기 vs 사용자 확인)뿐이므로, 추가 비용이 작고 가치가 크다.

**가이드 모드에서도 검증은 유효하다.** 읽기 경로가 살아 있다면 사용자가 옮긴 결과를 자동으로 확인해 잘못 옮겼을 때 알려줄 수 있다.
