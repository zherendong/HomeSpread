## 1. 밀어내기 규칙 실측

계획 엔진의 시뮬레이터는 실제 iOS 동작을 재현해야 한다. **문헌이나 기억이 아니라 대상 기기에서 직접 확인한다.**

### 확인할 항목

| 질문 | 왜 필요한가 |
|------|-----------|
| 아이콘을 앞쪽 슬롯에 놓으면 사이의 아이콘들이 어느 방향으로 밀리는가 | 시뮬레이터의 기본 규칙 |
| 뒤쪽 슬롯에 놓을 때는 반대로 당겨지는가 | 방향별로 규칙이 다를 수 있다 |
| 페이지가 꽉 찬 상태에서 밀림이 다음 페이지로 넘어가는가 | 넘어간다면 영향 범위가 전체 페이지다 |
| 넘어간 아이콘이 다음 페이지의 첫 슬롯에 오는가 | 위치 예측의 기준 |
| 마지막 페이지가 꽉 차면 새 페이지가 생기는가 | 페이지 수 변화 처리 |
| 페이지의 마지막 아이콘을 빼면 그 페이지가 사라지는가 | 페이지 인덱스가 바뀐다 |
| 드래그 중 페이지 경계에 머무르면 페이지가 넘어가는가, 대기 시간은 | 페이지 간 이동 제스처의 설계 |
| 폴더 위에 머무르면 폴더가 열리는가, 대기 시간은 | 폴더 통과 vs 폴더 진입의 구분 |

### 실측 방법

1. 알려진 초기 배치를 만든다 (아이콘 위치를 기록)
2. 이동 하나를 수행한다
3. 추출 파이프라인으로 결과를 읽는다
4. 초기 배치와 비교해 어느 아이콘이 어디로 갔는지 표로 만든다
5. 경계 조건(페이지 첫/마지막 슬롯, 꽉 찬 페이지)에서 반복

**결과를 `_workspace/`에 실측 기록으로 남긴다.** iOS 버전이 올라가면 다시 확인해야 하고, 그때 이전 기록이 비교 기준이 된다.

### 페이지 인덱스가 바뀌는 문제

페이지가 생기거나 사라지면 그 이후 페이지의 인덱스가 전부 밀린다. 계획의 남은 단계들이 **인덱스로 페이지를 지목하고 있으면 전부 엉뚱한 페이지를 가리키게 된다.**

두 가지 대응이 있다:

- 페이지를 안정적인 식별자(그 페이지의 대표 항목 등)로 지목한다
- 페이지 수 변화를 유발하는 연산 뒤에 재계획을 강제한다

후자가 단순하고 안전하다. 페이지 생성·소멸은 흔하지 않으므로 재계획 비용도 크지 않다.

## 2. 시뮬레이터 구현

시뮬레이터는 "이 연산을 적용하면 레이아웃이 어떻게 되는가"를 답하는 순수 함수다.

```
simulate(layout, operation) -> layout'
```

### 요구 사항

- **순수해야 한다.** 기기에 접근하지 않는다. 계획 탐색 중 수천 번 호출될 수 있다
- **`allowsGaps`에 따라 분기한다.** 상위 계층이 iOS 버전을 보지 않게 한다
- **실측 규칙을 그대로 반영한다.** 시뮬레이터가 실제와 다르면 계획이 매 단계 어긋나고, 재계획이 반복되어 예상 시간이 무너진다

### 시뮬레이터 검증

**시뮬레이터와 실제 기기의 일치를 테스트로 고정하라.** 실측 기록의 각 사례를 시뮬레이터에 통과시켜 같은 결과가 나오는지 확인한다. 이 테스트가 없으면 시뮬레이터의 오류가 실행 중 검증 실패로만 드러나고, 그때는 이미 사용자의 홈화면이 건드려진 뒤다.

## 3. 제스처 원시 동작

계획의 각 단계는 제스처 시퀀스로 번역된다.

| 원시 동작 | 구성 |
|----------|------|
| 편집 모드 진입 | 빈 곳 길게 누르기 (또는 아이콘 길게 누르기 → 메뉴에서 선택) |
| 같은 페이지 내 이동 | 누르기 → 목표 슬롯 중심으로 이동 → 떼기 |
| 페이지 간 이동 | 누르기 → 화면 가장자리로 이동 → **머무름** → 페이지 전환 후 목표로 → 떼기 |
| 폴더에 넣기 | 누르기 → 폴더 위로 → 짧게 머무름 → 떼기 (오래 머물면 폴더가 열린다) |
| 폴더에서 꺼내기 | 폴더 열기 → 아이콘 누르기 → 화면 가장자리로 → 폴더 밖으로 → 떼기 |
| 폴더 생성 | 누르기 → 대상 아이콘 위로 → 겹쳐진 상태에서 떼기 |
| 편집 모드 종료 | 완료 버튼 또는 홈 제스처 |

### 설계 원칙

- **슬롯 중심 좌표는 프로파일에서 계산한다.** 화면에 하드코딩된 픽셀 값을 쓰지 마라
- **드래그는 여러 중간 지점을 거친다.** 시작점에서 끝점으로 순간 이동하면 iOS가 드래그로 인식하지 않을 수 있다
- **각 단계 사이에 안정화 대기를 둔다.** 애니메이션 중에 다음 동작을 보내면 무시되거나 다른 곳에 떨어진다
- **머무름(dwell) 시간은 상수로 분리한다.** 기기·iOS 버전에 따라 조정이 필요하고, 코드 곳곳에 흩어져 있으면 조정할 수 없다

### 페이지 간 이동이 특히 어려운 이유

멀리 떨어진 페이지로 옮기려면 가장자리 머무름을 여러 번 반복해야 하고, 그동안 드래그를 유지해야 한다. 중간에 놓치면 아이콘이 엉뚱한 페이지에 떨어진다.

**대안을 검토하라**: 목표 페이지까지 여러 번 나눠 옮기는 것(중간 페이지 경유)이 한 번에 옮기는 것보다 안전할 수 있다. 안전성과 이동 횟수의 교환이므로, 비용 함수에 실패 확률을 반영해 결정한다.

## 4. 편집 모드 진입과 종료

### 진입

- 편집 모드에 들어가지 못한 상태에서 드래그를 보내면 **앱이 실행된다.** 이것이 가장 흔하고 가장 성가신 실패다
- 진입 후 실제로 편집 모드인지 **확인하고 진행한다.** 아이콘의 흔들림 상태나 완료 버튼의 존재로 판별할 수 있다
- 확인 없이 진행하지 마라. 앱이 실행되면 이후 모든 제스처가 그 앱에 전달된다

### 종료

- 작업 완료 시, 실패로 중단할 때, 사용자 취소 시 **모두 편집 모드를 종료한다**
- 편집 모드로 방치된 기기는 사용자가 다음에 집었을 때 혼란스럽다
- 종료도 확인한다. 종료 제스처가 실패했을 수 있다

### 예기치 않은 상태

실행 중 다음이 일어날 수 있다:

| 상황 | 대응 |
|------|------|
| 앱이 실행됨 | 홈으로 복귀 → 편집 모드 재진입 → 현재 상태 재추출 → 재계획 |
| 전화·알림이 화면을 덮음 | 대기 후 재시도, 반복되면 중단하고 사용자에게 알림 |
| 화면이 잠김 | 중단. 잠금 해제는 자동화 범위 밖이다 |
| USB 연결이 끊김 | 즉시 중단, 체크포인트 보존, 재연결 후 재개 제안 |

**모든 경우에 "현재 상태를 다시 읽는다"가 공통이다.** 예상 상태를 가정하고 이어가면 손상이 누적된다.

## 5. 제스처 실패 양상

실패가 오류로 보고되지 않는다는 것이 이 계층의 근본 문제다. 제스처는 성공적으로 전달됐지만 결과가 의도와 다를 수 있다.

| 양상 | 원인 | 감지 |
|------|------|------|
| 아이콘이 인접 슬롯에 떨어짐 | 좌표 오차, 프로파일 부정확 | 단계 검증에서 위치 불일치 |
| 아이콘이 폴더 안에 들어감 | 폴더 위 머무름 시간 초과 | 단계 검증에서 항목 소실 |
| 아무 일도 일어나지 않음 | 편집 모드 미진입, 길게 누르기 시간 부족 | 단계 검증에서 변화 없음 |
| 페이지가 넘어가지 않음 | 가장자리 머무름 부족 | 단계 검증에서 페이지 불일치 |
| 폴더가 새로 생성됨 | 아이콘 위에서 뗌 | 단계 검증에서 구조 변화 |

**모든 감지가 단계 검증에 의존한다.** 검증을 생략하면 이 실패들이 전부 조용히 누적된다. 이것이 SKILL.md가 매 단계 검증을 기본값으로 두는 이유다.

### 재시도 규칙

1. 1회 재시도한다 — 일시적 타이밍 문제가 흔하다
2. 재시도도 실패하면 그 단계를 `skipped`로 표시하고 **다음 단계로 진행한다**
3. 단, 스킵한 단계에 의존하는 이후 단계가 있으면 그것들도 스킵하거나 재계획한다
4. 연속 실패가 임계값에 도달하면 전체를 중단한다 — 구조적 문제(프로파일 오류, 편집 모드 이탈)의 신호다

**재시도 전에 현재 상태를 읽어라.** 첫 시도가 부분적으로 성공했다면(엉뚱한 곳에 떨어졌다면) 같은 제스처를 반복하는 것이 상황을 악화시킨다.

## 6. 체크포인트와 재개

### 무엇을 기록하나

```
Checkpoint
  planId          : 어느 계획인가
  completedSteps  : 완료한 단계 번호
  skippedSteps    : 스킵한 단계와 사유
  lastVerified    : 마지막으로 검증된 실제 레이아웃
  interruptedAt   : 중단 지점과 사유
```

`lastVerified`가 핵심이다. 재개할 때 이것이 있으면 전체 재추출 없이 이어갈 수 있고, 없으면 처음부터 다시 읽어야 한다.

### 재개 시 절차

1. 현재 실제 레이아웃을 추출한다
2. `lastVerified`와 비교한다
3. **같으면** 남은 단계를 그대로 이어간다
4. **다르면** — 사용자가 그 사이에 직접 홈화면을 만졌거나, 중단이 깨끗하지 않았다. 목표 레이아웃 기준으로 **처음부터 재계획한다**

4번을 생략하고 무조건 이어가는 구현을 만들지 마라. 사용자는 중단된 앱을 놔둔 채 기기를 쓴다.

### 재개를 제안할 때

- 중단 원인이 해소되었는지 먼저 확인한다 (연결 복구 등)
- 사용자에게 "22/30 단계까지 완료됨. 이어서 진행하시겠습니까?"를 보여준다
- 재계획이 필요한 경우(상태가 달라진 경우) 그 사실과 새 이동 횟수를 함께 제시한다
