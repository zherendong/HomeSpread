## 1. 实测顺延规则

模拟器需要再现目标环境的真实行为，不能把记忆或其他版本资料直接作为规则。

### 待回答的问题

| 问题 | 用途 |
|------|------|
| 拖到前方位置时，中间项目向哪边移动？ | 基本插入规则 |
| 拖到后方时是否按相反方向压紧？ | 区分方向 |
| 页面已满时，顺延是否跨页？ | 确定影响范围 |
| 溢出项目进入下一页哪个位置？ | 预测目标 |
| 最后一页已满时是否新增页面？ | 处理页数变化 |
| 移走页面最后一项后是否删页？ | 处理索引变化 |
| 拖动停留在边缘是否翻页，需多久？ | 跨页手势 |
| 停留在文件夹上是否打开，需多久？ | 区分经过与进入 |

### 实测步骤

1. 使用已获准的测试布局，记录初始位置和恢复限制。
2. 执行一次明确的移动。
3. 重新读取实际结果。
4. 逐项列出位置变化。
5. 对首尾位置、满页等边界情况分别验证。

把环境、日期、操作和结果保存在 `_workspace/` 的本次研究记录中。文档没有预先假定这些实验已经执行；版本变化时需要重新评估旧证据。

### 页面索引变化

新增或移除页面会改变后续索引，旧计划按数字引用的页面可能失效。

候选处理：

- 使用可验证的稳定页面身份，例如足以识别页面的内容特征；不能把不唯一的单个应用当成绝对身份。
- 任何页数变化后强制重读并重新规划。

后者实现较直接，但成本仍需测量，不凭经验保证页数变化罕见。

## 2. 实现模拟器

模拟器回答某个操作对布局的影响：

```text
simulate(layout, operation) -> layout'
```

要求：

- 纯函数，不访问设备，可在计划搜索中反复调用。
- 根据已定义能力，例如 `allowsGaps`，选择规则；不在上层到处判断版本。
- 精确遵循有证据的规则，未知行为不假装支持。

### 验证模拟器

将每个真实测量案例保存为输入和预期输出，作为回归样本。否则模拟器错误可能直到执行到用户设备上才暴露。

当前内存布局模型也有顺延规则，但这不等于已实现这里的触控模拟器；两者需要分别说明。

## 3. 手势原语

| 原语 | 候选序列 |
|------|----------|
| 进入编辑模式 | 长按空白处，或长按图标后选择对应菜单 |
| 同页移动 | 按下 → 移至目标中心 → 松开 |
| 跨页移动 | 按下 → 移到边缘 → 停留 → 等待翻页 → 移到目标 → 松开 |
| 放入文件夹 | 按下 → 到文件夹上 → 按已验证时间停留 → 松开 |
| 移出文件夹 | 打开 → 按住项目 → 移到外部 → 松开 |
| 创建文件夹 | 按住应用 → 移到另一应用上 → 按已验证条件松开 |
| 退出编辑模式 | 点击完成或执行已验证的主屏幕手势 |

这些是研究结构，实际路径和停留时间必须确认。

### 设计原则

- 位置中心由配置计算，不写死屏幕像素。
- 拖动使用必要的中间点；瞬间从起点跳到终点可能不被识别。
- 各阶段等待稳定，避免动画中发送下一动作。
- `dwell` 停留参数集中定义，并记录设备和版本依据。

### 跨远页的难点

连续边缘停留期间必须保持拖动，丢失按下状态可能落在中间页。可研究分段移动是否更可靠；这增加步骤，但可能降低失败成本。依据实测决定，不以“最少移动”牺牲可验证性。

## 4. 进入和退出编辑模式

### 进入

- 未进入编辑模式就拖动，可能启动应用。
- 在发送后续操作前，检查已验证的模式信号，例如完成按钮或对应树结构。
- 不以“已经发出长按”代替确认。若应用意外打开，之后的手势可能作用于应用内容。

### 退出

- 成功、失败与用户取消都应尝试退出编辑模式。
- 确认退出结果，失败时报告真实状态。
- 设备保持编辑模式会增加误触风险，不能悄悄留给用户处理。

### 意外状态

| 情况 | 研究方案的处理 |
|------|----------------|
| 应用意外启动 | 停止原计划，返回主屏幕，确认模式，重读并重新规划 |
| 来电或通知覆盖 | 暂停；按已定义限次策略处理，反复发生则停止并提示 |
| 设备锁定 | 停止，等待用户解锁；不自动处理密码 |
| USB 断开 | 停止并保留记录，重连后先重新读取 |

所有情况都必须以实际状态为依据，不能直接沿用旧预期。

## 5. 手势失败形式

协议成功传送手势，不等于界面结果正确。

| 现象 | 可能原因 | 发现方式 |
|------|----------|----------|
| 落到相邻位置 | 坐标或配置错误 | 位置比较 |
| 意外进入文件夹 | 停留或目标判断错误 | 检查文件夹层级，不能仅把页面上缺失当成应用丢失 |
| 没有变化 | 未进入编辑模式、长按不足 | 状态比较 |
| 没有翻页 | 边缘或停留条件不满足 | 页面比较 |
| 意外创建文件夹 | 在另一图标上松开 | 结构比较 |

这些都依赖逐步验证，不能只看手势调用是否返回成功。

### 重试规则

1. 先读取当前状态，判断第一次是否部分成功。
2. 仅对已确认不会扩大影响的瞬态失败，按预设次数重试，例如一次。
3. 再次失败则停止原步骤并重新规划；若标记 `skipped`，必须先重新核对所有后续依赖。
4. 连续失败达到阈值时停止整个执行，检查配置、模式或路径是否失效。

原文建议“失败后跳过并继续”，只有独立性已验证才成立。不能在未知实际状态上继续执行旧计划。

## 6. 检查点与恢复执行

### 记录内容

```text
Checkpoint
  planId          ：计划标识
  completedSteps  ：已完成步骤
  skippedSteps    ：跳过步骤及原因
  lastVerified    ：最近已验证的实际布局
  interruptedAt   ：中断位置和原因
```

`lastVerified` 提供比较基线，**不能免除恢复前的真实重读**。用户可能在应用中断后继续使用手机。

### 恢复步骤

1. 确认中断原因已经解除。
2. 重新读取实际布局。
3. 与 `lastVerified` 比较，并重新验证剩余操作的前提。
4. 状态一致且计划仍有效时，向用户确认继续。
5. 状态不同则依据当前状态与原目标重新规划，展示变化后的步骤和成本。

不能无条件按旧步骤索引继续。

### 向用户说明

- 例如：“已完成 22/30 步，是否继续？”数字为界面示例。
- 如需要重新规划，说明原因和新的步骤数。
- 明确当前部分完成状态及未完成项目；不要暗示存在事务回滚。
