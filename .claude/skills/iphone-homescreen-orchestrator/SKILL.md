# HomeSpread 开发协调流程

协调布局、设备通信、桌面界面与验证工作。按任务范围使用对应阶段，不因一次局部修改重做整个项目。

## 项目事实与安全边界

上游于 2026-08-19 纠正了“没有布局写入路径”的早期判断，依据见 `_workspace/01_ios-protocol-specialist_feasibility.md`。

未越狱 iPhone 可通过 `com.apple.springboardservices` 的 `getIconState` / `setIconState` 读取、写入整份 plist 布局。当前路径使用 USB 和信任配对，不需要越狱、开发者模式、Xcode 或 WebDriverAgent，也不依赖 OCR、无障碍树、逐步手势计划或断点续作。

| 事实 | 对应原则 |
|------|----------|
| `setIconState` 整体替换布局 | 保留未知内容与位置，不能仅按已理解字段重建（REQ-017） |
| 备份是恢复依据，不能保证完全撤销 | 写入前创建并校验备份，失败则不写（REQ-010）；明确 App 资源库应用回填无法由备份自动撤销 |
| 具体设备和 iOS 可能不接受写入 | 应用编辑要求本会话有有效写入验证标记；普通入口为明确确认的原样写回校验（REQ-003） |
| 设备可能在编辑期间改变 | 写入前重读并拒绝过期编辑；不声称该检查提供原子 CAS |
| 写入结果可能与请求不同 | 写后重读，检查丢失、移动、内容变化与新增项目 |

安全判断以用户布局为中心。Duo、含小组件、未知项或空位的当前/目标布局由统一能力检查拒绝所有写入，包括校验和恢复。以下会话规则只适用于通过能力检查的普通布局：原样写回校验失败时禁止应用编辑，但保留用户另行确认、选择同设备合格备份进行恢复的入口；恢复也可能失败。成功恢复并且读回比较通过，同样可建立本会话的写入验证标记。新读取或操作失败会使标记失效。

`layout-diff-planner` 保存的是历史回退研究。校验失败不会自动启用该方案，也不意味着已经有可运行的 WDA 或人工引导实现。

## 阶段 0：确认上下文

```text
_workspace/ 是否存在？
├─ 不存在                 → 从阶段 1 建立必要证据
├─ 存在，任务是局部修改   → 只执行受影响阶段和角色
├─ 存在，任务是继续       → 从未完成的位置继续
└─ 存在，方向发生变化     → 保留已有记录，先确定哪些结论仍然适用
```

原流程建议方向变化时把 `_workspace/` 改名为 `_workspace_prev/`。当前仓库保留历史文档和来源，未经明确需要不整体搬迁；若确需归档，先检查引用和重复目录，保留追踪关系。

1. 检查 `_workspace/`、`.claude/agents/`、`CLAUDE.md`。
2. 完整读取与任务有关的现有成果，确认进度与未验证事项。
3. 用简短说明告知将执行哪些阶段、由哪些角色负责。

局部修改也必须读取 `_workspace/02_contracts/` 中受影响的契约。

## 协作模式

| 阶段 | 模式 | 理由 |
|------|------|------|
| 1：可行性与需求 | 独立子任务，先并行调查再定义需求 | 调查可独立进行，需求依赖结果 |
| 2：设计 | 协作团队 | 契约需要互相协调 |
| 3：实现 | 协作团队与渐进 QA | 接口变更需要及时通知 |
| 4：集成验证 | 独立审查角色 | 避免只沿用实现者的假设 |

同一范围不启动相互竞争的团队；阶段切换保留成果文件。根据当前宿主提供的工具与并发限制安排成员。

上游 Claude 工作流写作 `TeamCreate`、`TaskCreate`、`run_in_background: true`，并要求 `model: "opus"`。这些名称保留为原流程术语；在其他宿主中映射到实际提供的协作能力，不能调用不存在的工具或声称使用未提供的模型。遵循当前会话对模型、委派和权限的更高优先级约定。

## 阶段 1：可行性与需求

### 1a：并行调查

| 角色 | 预期交付物 |
|------|------------|
| `ios-protocol-specialist` | `01_ios-protocol-specialist_feasibility.md`、需要时新建 `01_ios-protocol-specialist_verification-log.md` |
| `homescreen-model-analyst` | 需要时新建 `01_homescreen-model-analyst_model-draft.md`，记录模型与未解决问题 |

两项调查可独立进行。模型调查先定义主屏幕组成，使需求能描述具体对象和限制，而非仅说“便于整理”。

### 1b：依据调查定义需求

| 角色 | 输入 | 预期交付物 |
|------|------|------------|
| `product-strategist` | 1a 的结果与用户任务 | `01_product-strategist_requirements.md`；范围需要独立记录时创建 `01_product-strategist_scope.md` |

某项调查失败时，明确缺失证据并完成不受影响的工作，不能无限等待不存在的文件。

### 阶段门槛

设计决策需有相应可行性证据，尤其说明：

- 写入路径、前提、授权边界及真实验证范围。
- 当前整体读写的实际耗时；只有研究手势规划时才需要“单次移动耗时”作为成本函数输入。
- 工具许可证与分发条件。
- 明确的未验证事项。

不能以未验证结果宣称能力已成立。缺少真机写入授权时，继续实现和假设备测试，保留真机写入为未验证；需要用户决定范围或承担具体写入副作用时，说明具体选择及原因。

## 阶段 2：设计

角色及责任：

```text
homescreen-model-analyst  （layout-model 契约）
layout-sync-engineer      （sync-engine 契约）
desktop-app-architect     （依赖方向、ADR）
ui-engineer               （ui-viewmodel 契约）
```

`ios-protocol-specialist` 负责设备桥接契约。开始设计前，团队先读取它。

### 依赖顺序

```text
[1] 布局模型契约
 ↓
[2] 技术栈 ADR 与依赖方向
 ↓
[3] 同步层：备份、设备绑定、写前检查、写后验证
[4] 界面：画布、坐标、修改确认与进度（可与 3 并行）
 ↓
[5] 对照四份契约及实际数据流
```

历史手势方案才需要在第 3 步设计计划算法和成本函数。不要把它混入当前整体写入实现。

第 1 步是共同基础；第 5 步不能省略。核对坐标原点、单位、失败表达和进度事件，不能只确认每人写完了自己的文件。

### 团队沟通

- 修改契约前先通知负责人。
- 负责人向全部消费者说明改动。
- 冲突由主协调者判断，优先保护设备与原始布局。
- 阶段结束后明确每个成员的剩余职责，避免旧任务继续修改同一文件。

## 阶段 3：实现

```text
homescreen-model-analyst  （模型与原始数据解析）
layout-sync-engineer      （备份及受保护写入）
ui-engineer              （画布、编辑、确认和进度）
qa-inspector             （渐进验证）
```

设备桥接需要改动时由 `ios-protocol-specialist` 负责。并发数不足时按依赖顺序分批执行，不启动多名成员写同一文件。

### 当前实现顺序

```text
[1] 模型、约束、原始数据保留 → QA
[2] 读取与设备连接
[3] 备份、写前检查和写后比较（与 2 协调）→ 边界 QA
[4] 受保护写入及会话校验门槛
[5] 画布与编辑（1 完成后可并行）→ 边界 QA
[6] 确认、进度、结果和恢复入口
```

模型、备份、假设备和约束均可无真机测试。历史流程中的“模拟器、计划引擎、预演、人工引导”只在该回退方案明确进入范围时实施。

每个模块完成后检查它与已完成邻接模块。需要持续记录时建立 `03_qa-inspector_report.md`；该文件名是交付约定，存在与否要实际检查。

## 阶段 4：集成验证

安排独立 QA 角色，审查：

1. `native-integration-qa` 中的完整安全清单，不沿用早期“6 项”的过期计数。
2. 全部受影响边界。
3. REQ 验收追踪。
4. 未验证事项及原因。

需要独立报告时创建 `04_qa-inspector_final-report.md`，或更新本次任务已经采用的报告。

| 严重程度 | 处理 |
|----------|------|
| 最高：设备安全 | 修复后验证；未解决不能报告全部完成 |
| 高 | 修复并复验 |
| 中、低 | 说明影响；范围内且可逆的修复直接完成，存在实际取舍时再征求意见 |

## 阶段 5：交付与反馈

1. 说明完成内容与剩余限制。
2. 区分静态审查、假设备测试、真实只读与真实写入验证。
3. 如用户希望调整协作方式，再讨论角色和顺序；不要让可选的流程反馈阻塞交付。
4. 同步必要的契约、报告与 `CLAUDE.md` 记录，避免一份文档仍描述旧行为。

## 异常处理

| 情况 | 处理 |
|------|------|
| 子任务失败 | 可重试一次；仍失败则记录缺失，继续不受影响的工作 |
| 调查结论冲突 | 保留来源并列比较，依据证据裁决；需要用户范围选择时再询问 |
| 契约冲突 | 由负责人协调；负责人不明确时先分配 |
| 写入路径不可用 | 报告限制，禁止应用编辑；若要实施人工引导等替代产品，需要明确范围 |
| 缺少设备或授权 | 继续无设备工作，真实操作标记未验证 |
| 许可证不符合分发方案 | 触发 ADR 复审，评估合法替代方案 |

## 场景示例

### 正常流程示例

用户请求：“制作在电脑上编辑主屏幕的功能。”

1. 阶段 0 检查现有记录；无记录则从阶段 1 开始。
2. 并行确认设备服务与布局格式。只有实际执行后才能记录耗时和成功结果。
3. 根据证据确定 REQ 范围。
4. 完成契约、ADR 和交叉审查，修正位置原点等不一致。
5. 分模块实现并渐进测试。
6. 独立 QA 报告通过、失败和未验证项。
7. 交付可运行结果及具体限制。

早期示例中的“WDA 单次移动 3.2 秒”“安全 6 项通过”“修复 2 个缺陷”是流程示意，不是本次项目的实测记录。

### 历史回退研究示例

协议研究发现目标版本无法使用当前布局写入路径，且 WDA 也未验证：

1. 不把未验证路径当成可用能力。
2. 完成不依赖真实写入的研究，向用户说明限制。
3. 如需要范围决定，可选择在获准后做具体真机验证，或另行实现人工引导。
4. 只有用户明确选择替代范围后，才重新安排需求和设计。人工引导可复用历史计划模型，但不代表现有产品已包含它。
