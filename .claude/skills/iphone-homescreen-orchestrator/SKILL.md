# HomeBoard 오케스트레이터

여러 홈화면 페이지를 PC 한 화면에 펼쳐 놓고 편집하는 Windows 앱을 만드는 팀을 조율한다.

## 이 프로젝트를 지배하는 사실

> 2026-08-19 갱신. 이전 판본은 "쓰는 API가 없다"고 적었으나, 조사 결과 틀린 것으로 확인되었다.
> 근거: `_workspace/01_ios-protocol-specialist_feasibility.md`

**비탈옥 iPhone에도 홈화면을 쓰는 경로가 있다.** `com.apple.springboardservices` 의
`getIconState` / `setIconState` 로 레이아웃 전체를 plist 하나로 읽고 쓴다. 탈옥·개발자 모드·
Xcode·WebDriverAgent 없이 USB 연결과 "신뢰"만으로 동작한다. 제스처 재생, 접근성 트리 파싱,
OCR, 밀어내기 시뮬레이션, 체크포인트/재개는 **전부 불필요하다.**

대신 새로운 위험이 그 자리를 대신한다:

| 사실 | 따라 나오는 원칙 |
|------|----------------|
| `setIconState` 는 **부분 수정이 아니라 전체 덮어쓰기**다 | 우리가 해석하지 못한 요소(위젯 등)를 빠뜨리면 그대로 사라진다 → **원본 보존(REQ-017)** |
| 직전 상태를 그대로 다시 쓰면 완전히 복구된다 | 되돌리기가 진짜로 가능하다 → **백업 무결성(REQ-010)**. 백업 실패는 곧 쓰기 중단 |
| 특정 기기·iOS 버전에서 거부될 수 있다 `[미검증]` | 편집 기능을 켜기 전에 **항등 왕복 안전 시험(REQ-003)**을 통과해야 한다 |

안전성의 축은 "중단 안전성"이 아니라 **"백업 무결성"과 "원본 보존"**이다. 결정이 갈릴 때는
여전히 **"이것이 사용자의 홈화면을 위험하게 하는가"**를 먼저 묻는다.

**항등 왕복 시험이 실패하면** 쓰기 기능을 만들지 않고 `layout-diff-planner` (폴백 경로)로
되돌아간다. 그 스킬은 이 경우를 위해 보존되어 있다.

## Phase 0: 컨텍스트 확인 (항상 먼저)

```
_workspace/ 존재?
├─ 없음                          → 초기 실행 (Phase 1부터)
├─ 있음 + 부분 수정 요청          → 부분 재실행 (해당 에이전트만)
├─ 있음 + 이어서 진행 요청        → 중단 지점부터 재개
└─ 있음 + 새로운 입력/방향 전환    → _workspace/ → _workspace_prev/ 로 이동 후 초기 실행
```

1. `_workspace/`, `.claude/agents/`, `CLAUDE.md`를 확인한다
2. 기존 산출물이 있으면 **읽고** 현재 진행 지점을 파악한다
3. 실행 계획(어느 Phase부터, 어느 에이전트를)을 사용자에게 한 문단으로 보고한 뒤 진행한다

부분 재실행 시에도 **계약 파일(`_workspace/02_contracts/`)은 반드시 읽는다.** 계약을 모르는 상태의 재실행은 경계면을 깨뜨린다.

## 실행 모드: 하이브리드

| Phase | 모드 | 이유 |
|-------|------|------|
| 1. 타당성·요구 | 서브 에이전트 (병렬 + 순차) | 조사 둘은 독립적. 요구 정의는 그 결과에 의존 |
| 2. 설계 | **에이전트 팀** | 계약을 서로 맞춰야 한다. 실시간 조율 필수 |
| 3. 구현 | **에이전트 팀** | 계약 변경·질의가 오간다. 점진적 QA 포함 |
| 4. 통합 검증 | 서브 에이전트 | 독립성이 검증의 가치다 |

**팀은 세션당 하나만 활성이다.** Phase 2 팀을 정리한 뒤 Phase 3 팀을 만든다. 산출물은 파일로 남아 있으므로 팀이 바뀌어도 이어진다.

**모든 Agent 호출에 `model: "opus"`를 명시한다.**

## Phase 1 — 타당성과 요구 (서브 에이전트)

두 단계로 나눈다. 요구 정의는 타당성 결과에 의존하므로 병렬로 둘 수 없다.

### 1a. 조사 (병렬, `run_in_background: true`)

| 에이전트 | 산출물 |
|---------|--------|
| `ios-protocol-specialist` | `01_ios-protocol-specialist_feasibility.md`, `01_ios-protocol-specialist_verification-log.md` |
| `homescreen-model-analyst` | `01_homescreen-model-analyst_model-draft.md` (모델 초안 + 미해결 질문) |

두 조사는 서로를 필요로 하지 않는다. 모델 초안은 "홈화면이 무엇으로 이루어져 있는가"를 먼저 정리해, 요구사항이 막연한 표현("정리하기 쉽게")이 아니라 모델 용어로 쓰이게 한다.

### 1b. 요구 정의 (1a 완료 후)

| 에이전트 | 입력 | 산출물 |
|---------|------|--------|
| `product-strategist` | 1a의 두 산출물 + 사용자 요구 설명 | `01_product-strategist_requirements.md`, `01_product-strategist_scope.md` |

1a 중 하나가 실패해 산출물이 없으면, 그 사실을 입력에 명시하고 진행한다. 없는 파일을 기다리며 정지하지 않는다.

### 이 Phase의 관문

**타당성 결과 없이 Phase 2로 넘어가지 않는다.** 특히 다음이 확정되어야 한다:

- 쓰기 경로가 실제로 가능한가, 어떤 사전 조건에서
- 아이콘 1개 이동의 **실측 소요 시간** (비용 함수의 입력)
- 채택 후보 도구의 라이선스와 배포 가능성
- `[미검증]`으로 남은 항목의 목록

`[미검증]` 항목 위에 제품 결정을 세우지 않는다. 미검증이 많으면 그 사실을 사용자에게 보고하고, 검증할지 가정하고 진행할지 확인받는다.

## Phase 2 — 설계 (에이전트 팀)

`TeamCreate`로 4명 팀 구성:

```
homescreen-model-analyst   (계약 소유: layout-model)
layout-sync-engineer       (계약 소유: sync-engine)
desktop-app-architect      (계약: 의존 방향, ADR)
ui-engineer                (계약 소유: ui-viewmodel)
```

`ios-protocol-specialist`는 Phase 1에서 `device-bridge.contract.md`를 남긴다. 팀은 이를 읽고 시작한다.

### 작업 순서 (TaskCreate 의존성)

```
[1] 레이아웃 모델 계약 확정        ← 다른 모든 것의 기반
     ↓
[2] 스택 ADR + 의존 방향 확정      ← 타당성 결과에 의존
     ↓
[3] 동기화 엔진 설계 (계획 알고리즘, 비용 함수, 안전 규약)
[4] UI 설계 (화면, 좌표계, 뷰모델 계약)     ← [3]과 병렬
     ↓
[5] 계약 상호 검토 — 네 계약을 나란히 놓고 대조
```

**[1]이 흔들리면 나머지가 전부 흔들린다.** 여기에 가장 많은 시간을 쓴다.

**[5]를 생략하지 마라.** 각자 계약을 쓴 것과 네 계약이 맞물리는 것은 다른 문제다. 이 단계에서 좌표 원점, 단위, 부분 실패 표현, 진행 이벤트를 교차 확인한다.

### 팀 통신 규칙

- 계약을 바꾸려면 **소유자에게 먼저 알린다.** 소비자가 자기 쪽만 고치지 않는다
- 소유자는 변경을 전원에게 브로드캐스트한다
- 상충하는 설계는 리더가 중재하되, **기기 안전성 쪽 주장이 우선한다**

Phase 2 종료 시 팀을 정리한다.

## Phase 3 — 구현 (에이전트 팀)

`TeamCreate`로 팀 구성. 구현 담당 3명 + QA 1명:

```
homescreen-model-analyst   (모델 + 추출 파이프라인)
layout-sync-engineer       (계획 엔진 + 실행 루프)
ui-engineer                (캔버스 + 편집 + 진행 화면)
qa-inspector               (점진적 검증)  ← general-purpose 타입
```

`ios-protocol-specialist`는 기기 브리지 구현이 필요할 때 서브 에이전트로 호출한다.

### 구현 순서

```
[1] 레이아웃 모델 + 제약 검사 + 시뮬레이터   ← 기기 없이 테스트 가능
     ↓  QA 검증
[2] 추출 파이프라인
[3] 계획 엔진                                ← [2]와 병렬 가능
     ↓  QA 검증 (경계면)
[4] 실행 루프 + 안전 규약
[5] UI 캔버스 + 편집                         ← [1] 이후 병렬 가능
     ↓  QA 검증 (경계면)
[6] 드라이런 / 진행 / 완료 화면
[7] 가이드 모드
```

**[1]을 먼저 완성한다.** 기기 없이 테스트할 수 있는 유일한 덩어리이고, 시뮬레이터의 정확성이 나머지 전부의 전제다.

### 점진적 QA

**모듈이 완성될 때마다** `qa-inspector`가 그 모듈과 이미 완성된 이웃의 경계를 검증한다. 전체 완성 후 1회 검증은 늦다 — 경계면 결함은 양쪽을 모두 고쳐야 하고, 늦게 발견될수록 고칠 것이 많다.

QA 결과는 `03_qa-inspector_report.md`에 누적한다.

Phase 3 종료 시 팀을 정리한다.

## Phase 4 — 통합 검증 (서브 에이전트)

`qa-inspector`를 **독립 서브 에이전트**로 호출한다. 팀에서 분리하는 이유는 구현 논의에 물들지 않은 시선을 얻기 위해서다.

검증 범위:

1. 기기 안전성 필수 6항목
2. 모든 경계면 교차 비교
3. 수용 기준(REQ ID) 전수 추적
4. 미검증 항목 명시

산출물: `04_qa-inspector_final-report.md`

### 결함 처리

| 심각도 | 처리 |
|--------|------|
| 최상 (기기 안전성) | **즉시 수정.** 미수정 상태로 완료 보고 금지 |
| 상 | 수정 후 재검증 |
| 중·하 | 사용자에게 보고하고 우선순위 확인 |

## Phase 5 — 보고와 피드백

1. 무엇이 완성되었고 무엇이 남았는지 정리해 보고한다
2. **미검증 항목을 반드시 함께 보고한다.** 기기·도구 부재로 확인하지 못한 것을 통과로 표시하지 않는다
3. 하네스 개선 피드백을 요청한다 — "에이전트 구성이나 순서에 바꾸고 싶은 점이 있나요?"
4. 변경 사항을 `CLAUDE.md`의 변경 이력에 기록한다

## 에러 핸들링

| 상황 | 처리 |
|------|------|
| 에이전트 실패 | 1회 재시도. 재실패 시 그 산출물 없이 진행하되 **보고서에 누락을 명시** |
| 조사 결과가 상충 | 삭제하지 말고 출처를 병기해 함께 남긴다. 리더가 판단하거나 사용자에게 확인 |
| 계약 충돌 | 소유자 우선. 소유자가 불명확하면 리더가 소유자를 지정한 뒤 진행 |
| 타당성 조사에서 쓰기 경로 불가 판정 | **Phase 2 진입 전 사용자에게 보고.** 가이드 모드 중심 제품으로 범위를 재조정할지 확인 |
| 기기가 없어 검증 불가 | 진행하되 `미검증`으로 표시. 통과로 표시 금지 |
| 외부 도구 라이선스 문제 | ADR 재검토 트리거. 대체 후보로 전환 검토 |

## 테스트 시나리오

### 정상 흐름

사용자: "홈화면을 PC에서 편집하는 기능을 만들어줘"

1. Phase 0 — `_workspace/` 없음 → 초기 실행
2. Phase 1a — 타당성 조사와 모델 초안을 병렬 수행. 이동 1회 실측 3.2초, WDA 경로 `[확인됨]`, 감독 모드 경로 `[미검증]`
3. Phase 1b — 두 산출물을 받아 요구·범위 확정 (REQ-001~REQ-024)
4. Phase 2 — 4인 팀. 레이아웃 모델 계약 확정 → 스택 ADR → 엔진·UI 설계 → 계약 상호 검토에서 슬롯 원점 불일치 발견·수정
5. Phase 3 — 모델·시뮬레이터부터 구현, 모듈마다 QA
6. Phase 4 — 독립 QA. 안전성 6항목 통과, 경계면 결함 2건 수정
7. Phase 5 — 보고 + 피드백 요청

### 에러 흐름

Phase 1에서 `ios-protocol-specialist`가 "대상 iOS 버전에서 WDA 자동화 경로 동작을 확인할 수 없음 `[미검증]`"으로 보고.

1. 리더가 관문에서 정지 — 미검증 위에 제품을 세우지 않는다
2. 사용자에게 보고: 자동 적용 경로가 불확실함, 두 선택지 제시
   - (a) 실기기 검증 후 진행
   - (b) 가이드 모드를 MVP로 삼고 자동 적용을 후속으로
3. 사용자가 (b)를 선택 → `product-strategist`를 재호출해 범위 재조정
4. Phase 2는 조정된 범위로 시작. 계획 엔진은 그대로 필요하다 (가이드 모드도 같은 계획을 쓴다)
