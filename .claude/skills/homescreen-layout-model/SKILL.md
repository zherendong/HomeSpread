# Homescreen Layout Model — 홈화면 구조의 데이터 모델

홈화면이라는 불규칙한 구조를 안정적인 데이터 모델로 환원하고, 실제 기기에서 그 모델을 채우는 방법.

## 왜 모델이 먼저인가

이 앱의 세 모듈 — UI, 동기화 엔진, 추출 파이프라인 — 은 모두 "홈화면이 무엇으로 이루어져 있는가"에 대한 **하나의 합의된 표현**을 필요로 한다. 이 표현이 흔들리면 세 모듈이 서로 다른 홈화면을 상상하게 되고, 그 불일치는 컴파일 시점에 드러나지 않는다. 사용자가 적용 버튼을 누른 뒤에야 드러난다.

그래서 모델은 코드보다 먼저 확정되고, 확정된 뒤에는 계약으로 취급된다. 변경할 때는 `interface-contract` 규약에 따라 버전을 올리고 브로드캐스트한다.

## 모델의 두 인스턴스

같은 스키마를 쓰지만 의미가 다른 두 개가 항상 공존한다:

| 인스턴스 | 의미 | 출처 |
|---------|------|------|
| `observed` | 지금 기기에 실제로 있는 상태 | 추출 파이프라인 |
| `desired` | 사용자가 만들고자 하는 상태 | UI 편집 |

동기화 엔진은 이 둘의 차이를 계산한다. UI는 이 둘을 시각적으로 구분해 보여준다. **하나의 "현재 레이아웃" 변수로 뭉뚱그리면 안 된다** — 그러면 사용자는 자기가 편집한 것이 이미 기기에 반영됐다고 착각한다.

## 스키마 구성 요소

### 계층

```
Layout
 ├─ deviceProfile   (그리드 능력 — 아래 "기기 프로파일")
 ├─ pages[]         (순서 있음)
 │   └─ slots       (행×열 격자, 각 칸은 비었거나 항목 하나)
 │       └─ item    : AppIcon | Folder | Widget | Unknown
 ├─ dock            (별도 컨테이너, 별도 용량)
 └─ unplaced[]      (설치되어 있으나 홈화면에 없는 앱 — 편집 시 "추가" 소스)
```

### 항목 타입

| 타입 | 필수 필드 | 주의 |
|------|----------|------|
| `AppIcon` | `displayIdentifier`, 표시 이름 | **`displayIdentifier` 가 정식 키다** (아래 실측 형식 참조). 표시 이름은 표시용 |
| `Folder` | 폴더 이름, 내부 페이지들 | 폴더 안에 폴더는 없다 — 타입으로 강제하라 |
| `Widget` | 앵커 슬롯, 점유 크기, (가능하면) 소유 앱 | 여러 슬롯을 점유. 아래 "위젯 표현" 참조 |
| `Unknown` | 슬롯 위치, 원본 단서 | 인식 실패. **버리지 말 것** |

### [확인됨] iconState 의 실제 형태 (iPhone 14, iOS 26.1 · 2026-08-19)

실기기 덤프 309개 항목을 전수 조사한 결과, 형태는 **네 가지뿐**이었다:

| 형태 | 키 구성 | 관측 수 |
|------|--------|--------|
| 설치된 앱 | `bundleIdentifier` · `bundleVersion` · `displayIdentifier` · `displayName` · `iconModDate` | 204 |
| **오프로드된 앱** | `displayIdentifier` · `displayName` | 77 |
| 웹 클립 | `displayIdentifier` · `displayName` · `iconModDate` · `webClipURL` | 2 |
| 폴더 | `displayName` · `listType: "folder"` · `iconLists[][]` | 26 |

**항목의 정체성은 `bundleIdentifier` 가 아니라 `displayIdentifier` 다.** 처음에는 번들 ID를 정식 키로 가정했고, 그 결과 실기기 첫 실행에서 79개(전체의 26%)가 `Unknown` 으로 분류되었다. 오프로드된 앱 — 아이콘만 남기고 본체를 지운 상태 — 에는 `bundleIdentifier` 가 아예 없기 때문이다.

`Unknown` 은 안전을 위해 움직일 수 없게 만드는 타입이다. 그러니 이 오해 하나가 **사용자 앱의 4분의 1을 UI에서 얼려버린다.** 형식 가정을 실기기로 확인하기 전에는 UI를 만들지 않는 이유가 이것이다.

관측되지 않은 것도 기록해 둔다: **위젯은 iconState 에 나타나지 않았다** (이 기기의 홈화면에는 위젯이 없었다). 빈칸도 0개였다 — 페이지는 24칸(4열×6행)이 꽉 찬 상태로만 나타났다. 위젯이 있는 기기에서 다시 확인해야 한다 `[미검증]`.

### Unknown을 1급 타입으로 두는 이유

인식은 실패한다. 위젯, 시스템 항목, 테마가 적용된 아이콘, 새로운 iOS 기능은 모두 파서가 모르는 형태로 나타날 수 있다.

이때 선택지는 둘뿐이다: 버리거나, 표시하거나.

버리면 그 슬롯이 **빈칸으로 보인다.** 그러면 UI는 사용자에게 빈 자리를 보여주고, 사용자는 거기에 아이콘을 옮기고, 동기화 엔진은 그 이동을 계획하고, 실제 기기에서는 그 자리에 있던 무언가가 밀려난다. 사용자는 자기 앱이 사라졌다고 느낀다.

그래서 `Unknown`은 반드시 1급 타입이어야 한다. **"읽지 못함"과 "비어 있음"은 다른 것이다.**

## 신뢰도

모든 항목이 `confidence`를 갖는다. 이것은 장식이 아니라 **동작을 결정하는 필드**다.

| 신뢰도 | UI 표시 | 적용 계획 포함 |
|-------|--------|--------------|
| 높음 | 일반 | 포함 |
| 중간 | 약한 표시 | 포함 |
| 낮음 / `Unknown` | 명확히 구분 표시 | **사용자 확인 전까지 제외** |

낮은 신뢰도 항목을 조용히 계획에 넣으면, 잘못 식별한 아이콘을 엉뚱한 곳으로 옮기게 된다. 되돌릴 수 없는 동작이므로 보수적으로 처리한다.

## 기기 프로파일

그리드 수치는 **기기마다 다르고, 같은 기기에서도 사용자 설정에 따라 다르다.** 화면 크기, 디스플레이 확대 설정, 텍스트 크기 설정이 모두 영향을 준다.

따라서:

- **수치를 코드에 하드코딩하지 마라.** 별도 프로파일 테이블로 분리한다
- 프로파일에 담을 것: 페이지 행×열, 독 슬롯 수, 폴더 페이지당 용량, 폴더 최대 페이지, 홈화면 최대 페이지, 능력 플래그
- **능력 플래그**를 함께 제공하여 상위 계층이 iOS 버전 분기를 하지 않게 한다. 대표적으로 "아이콘 사이 빈칸을 허용하는가" — iOS 버전에 따라 다르며, 이 하나가 계획 알고리즘 전체를 바꾼다
- **알 수 없는 기기의 폴백**: 스크린샷에서 아이콘 간격을 실측해 그리드를 추정한다. 추정했다는 사실을 프로파일에 표시한다
- 프로파일 수치에도 `[확인됨]` / `[문헌]` / `[미검증]` 표기를 적용한다

### 프로파일이 틀렸다는 신호

**두 항목이 같은 슬롯으로 계산되면 프로파일이 틀린 것이다.** 이 충돌은 추출 단계에서 즉시 감지할 수 있고, 감지하면 그 기기의 프로파일을 신뢰해서는 안 된다. 상세는 `references/grid-constraints.md` 참조.

## 앱 식별

표시 이름은 키가 될 수 없다 — 지역화되고, 중복되고, 바뀐다. 번들 ID만이 안정적이다.

식별 절차는 `ios-device-protocol` 스킬의 `references/capture-and-structure.md`가 다룬다. 모델 관점에서 지켜야 할 것은 하나다: **번들 ID를 확정하지 못한 항목은 `AppIcon`이 아니라 `Unknown`이다.** 표시 이름만 가지고 `AppIcon`을 만들면, 그 항목은 이후 모든 단계에서 진짜인 척한다.

## 직렬화

사용자가 레이아웃을 저장·복원할 수 있어야 한다면 직렬화 형식이 필요하다.

- **스키마 버전 필드를 처음부터 넣는다.** 나중에 추가하면 이전 파일을 구분할 수 없다
- 저장 파일에는 `desired` 레이아웃과 함께 **어떤 기기 프로파일 기준으로 만들어졌는지**를 기록한다. 다른 기기에서 열었을 때 그리드가 다르면 그대로 적용할 수 없다
- 앱을 번들 ID로 저장한다. 표시 이름은 참고용으로만 함께 저장한다 (복원 시 앱이 삭제되어 있으면 이름이라도 보여줄 수 있다)
- 복원 시 현재 설치된 앱과 대조하여, 없는 앱을 명시적으로 보고한다

## 스키마 확정 전 반드시 답할 질문

1. 같은 앱이 홈화면에 두 번 나타날 수 있는가? 모델이 이를 허용하는가?
2. 위젯의 점유를 앵커+크기로 표현하는가, 점유 슬롯 집합으로 표현하는가? (`references/grid-constraints.md`의 "위젯 표현" 참조)
3. 페이지 숨김 상태를 표현하는가?
4. 폴더 이름의 자동 생성 여부를 구분해야 하는가?
5. `unplaced`(홈화면에 없는 설치 앱)를 모델에 포함하는가? 편집 UI에서 앱을 "추가"하려면 필요하다
6. 슬롯 인덱스의 원점과 방향은? (좌상단 0,0 · 행 우선 — 명시하지 않으면 모듈마다 다르게 해석한다)

## 쓰기 경로와 안전 규칙 (2026-08-19 추가)

레이아웃을 기기에 반영하는 것은 `setIconState` 호출 하나다. 계획도, 제스처도, 재개도 없다.
대신 이 호출의 성질 때문에 아래 규칙이 강제된다.

### 전체 덮어쓰기라는 사실

보내지 않은 것은 사라진다. 부분 갱신이 아니다. 여기서 두 가지가 따라 나온다.

**1. 쓸 상태는 언제나 읽은 원본에서 파생시킨다.** 우리 모델로 재구성해서 쓰면, 모델이
표현하지 못하는 것(위젯, 새 iOS 기능)이 전부 사라진다. 해석은 원본 위에 얹는 **뷰**이고,
쓰기는 원본을 편집한 결과여야 한다. `Unknown`을 1급 타입으로 두는 이유가 여기서 완성된다 —
표시하기 위해서가 아니라 **잃지 않기 위해서**다.

**2. Unknown 항목은 움직이지 않는다.** 어떤 배치 제약이 걸려 있는지 모르는 것을 옮기면
무엇이 깨지는지도 알 수 없다. 화면에는 보여 주되 드래그 대상에서 제외한다.

### 백업 무결성

되돌리기는 "직전 상태를 그대로 다시 쓰는 것"이므로 진짜로 완전하다. 그래서 이 프로젝트의
안전성은 정교한 검증이 아니라 **백업이 반드시 존재한다**는 사실에 걸려 있다.

- 쓰기 경로는 하나로 모은다 (`backup.guarded_write`). 여러 곳에서 직접 쓰면 언젠가
  백업 없는 경로가 하나 생기고, 사고는 거기서 난다
- **백업 저장 실패는 곧 쓰기 중단이다.** 백업 없이 쓰는 것보다 아무것도 하지 않는 편이 낫다
- 저장 직후 되읽어 원본과 대조한다. '파일은 만들어졌지만 복원할 수 없는' 백업은
  없는 것보다 나쁘다 — 되돌릴 수 있다고 믿게 만들기 때문이다

### 항등 왕복 안전 시험

편집 기능을 켜기 전에 통과해야 하는 관문이다. 읽은 상태를 **한 글자도 바꾸지 않고** 다시 쓰고,
다시 읽어서 같은지 본다.

- 통과: 쓰기 경로가 성립하고, 원본을 온전히 왕복시킬 수 있다
- 실패: 이 기기·이 iOS 버전에서 쓰기 기능을 만들지 않는다. `layout-diff-planner` 폴백으로 간다

비교할 때 **휘발성 필드는 제외한다.** `iconModDate` 처럼 기기가 갱신하는 값으로 판정하면
정상 동작이 항상 불일치로 보고되고, 그러면 시험 자체가 무의미해진다.
