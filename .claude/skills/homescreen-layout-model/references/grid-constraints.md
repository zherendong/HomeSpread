## 1. 수치를 확정하는 방법

그리드 수치(행×열, 독 슬롯, 폴더 용량, 최대 페이지)는 기기 모델·화면 크기·디스플레이 확대 설정·텍스트 크기 설정에 따라 달라진다. 그리고 iOS 버전에 따라서도 바뀔 수 있다.

**기억에 의존해 표를 채우지 마라.** 다음 순서로 확정한다:

1. **실측이 최우선** — 대상 기기에서 스크린샷을 찍고 아이콘 중심 간격을 측정한다. 이것이 `[확인됨]`이다
2. **문헌 확인** — 확인 가능한 출처가 있으면 `[문헌]`으로 기록하고 출처를 병기
3. **미확인은 미확인으로** — `[미검증]` 프로파일 위에 적용 계획을 세우지 않는다

프로파일이 부정확하면 슬롯 좌표가 어긋나고, 어긋난 좌표로 제스처를 재생하면 아이콘이 엉뚱한 곳으로 간다. 이 오류는 되돌릴 수 없으므로 다른 어떤 부정확함보다 비싸다.

### 실측 폴백 절차

알 수 없는 기기를 만났을 때:

1. 홈화면 스크린샷 획득
2. 아이콘 후보 영역 검출 (규칙적으로 반복되는 정사각 영역)
3. 수평·수직 방향의 중심 간격을 구해 열 수·행 수 산출
4. 독 영역(하단의 별도 배경)을 분리해 독 슬롯 수 산출
5. 결과를 프로파일로 저장하고 `추정됨` 플래그를 붙인다

추정 프로파일임을 상위 계층에 반드시 전달하라. UI는 이 경우 사용자에게 확인을 요청할 수 있어야 한다.

## 2. 빈칸 규칙 — 계획을 바꾸는 하나의 플래그

홈화면의 아이콘 배치 규칙에는 두 가지 모드가 있을 수 있다:

| 모드 | 규칙 | 결과 |
|------|------|------|
| **조밀 채움** | 아이콘이 좌상단부터 순서대로 채워지고 중간에 빈칸을 둘 수 없다 | 한 아이콘을 빼면 뒤의 모든 아이콘이 앞으로 당겨진다 |
| **자유 배치** | 임의 슬롯에 배치 가능, 빈칸 허용 | 아이콘을 빼도 다른 아이콘이 움직이지 않는다 |

**이 차이가 계획 알고리즘 전체를 결정한다.**

조밀 채움 모드에서 레이아웃은 사실상 **순서 있는 리스트**다. 슬롯 좌표는 리스트 인덱스의 표현일 뿐이고, 하나를 옮기면 그 사이의 모든 아이콘이 한 칸씩 밀린다. 자유 배치 모드에서 레이아웃은 **희소 격자**이고, 한 아이콘의 이동이 다른 아이콘에 영향을 주지 않는다.

따라서:

- 프로파일에 `allowsGaps` 능력 플래그를 반드시 둔다
- 모델은 두 모드를 모두 표현할 수 있어야 한다 (희소 격자로 표현하고, 조밀 모드에서는 불변식으로 강제)
- **상위 계층이 iOS 버전을 직접 분기하지 않게 한다.** 계획 엔진은 `allowsGaps`만 보고 동작해야 한다
- 이 플래그의 값은 대상 iOS 버전에서 **실측으로 확인**한다

## 3. 위젯 표현

위젯은 여러 슬롯을 점유한다. 표현 방식은 두 가지다:

| 방식 | 장점 | 단점 |
|------|------|------|
| **앵커 슬롯 + 크기** | 저장이 간결, 이동이 자연스러움 | 점유 여부를 물으려면 매번 계산 |
| **점유 슬롯 집합** | 충돌 검사가 단순 | 중복 정보, 이동 시 전체 갱신 |

**권장: 앵커+크기를 정식 표현으로 두고, 점유 집합은 파생 값으로 계산한다.** 두 표현을 모두 저장하면 반드시 어긋난다.

모델에 필요한 것:

- 앵커 슬롯 (행, 열)
- 크기 (행 수 × 열 수)
- 소유 앱의 번들 ID (알 수 있는 경우)
- 위젯 종류 식별자 (알 수 있는 경우)

**주의**: 위젯은 접근성 트리에서 라벨이 불명확하거나 없을 수 있다. 크기만 알고 정체를 모르는 위젯은 `Widget` 타입에 `unresolved` 신뢰도를 부여한다. **이 경우 이동 계획에서 제외한다** — 위젯 이동은 아이콘 이동보다 실패 시 복구가 어렵다.

### 충돌 검사

새 항목을 배치할 때 확인할 것:

- 앵커가 격자 범위 안인가
- 앵커 + 크기가 격자 범위를 벗어나지 않는가
- 점유 영역이 다른 항목의 점유 영역과 겹치지 않는가
- 위젯 크기가 해당 프로파일에서 허용되는 크기 목록에 있는가

이 검사는 **UI가 드롭 전에** 호출해야 한다. 드롭 후에 거부하면 편집이 답답해진다.

## 4. 폴더 제약

- 폴더 안에 폴더는 없다 → **타입 시스템으로 강제하라.** 재귀 타입으로 정의하면 언젠가 중첩 폴더가 만들어진다
- 폴더는 내부에 여러 페이지를 가질 수 있다 → 폴더 내부도 페이지 리스트다
- 폴더 페이지당 용량과 최대 페이지 수는 프로파일 값이다
- 폴더 이름은 자동 생성될 수 있고 사용자가 바꿀 수 있다

### 폴더 관련 편집 연산의 비용

| 연산 | 실제 기기에서 필요한 동작 |
|------|------------------------|
| 폴더에 앱 넣기 | 아이콘을 폴더 위로 드래그 |
| 폴더에서 앱 꺼내기 | 폴더 열기 → 아이콘을 폴더 밖으로 드래그 → 폴더 닫기 |
| 폴더 생성 | 아이콘을 다른 아이콘 위로 드래그 |
| 폴더 해체 | 내부 아이콘을 하나씩 전부 꺼냄 |
| 폴더 이름 변경 | 폴더 열기 → 이름 편집 → 확정 |

**폴더 해체는 내부 아이콘 수만큼의 이동이다.** 계획 엔진이 이 비용을 균일하게 매기면 예상 시간이 크게 빗나간다. 상세는 `layout-diff-planner` 스킬 참조.

## 5. 독

독은 페이지와 별개의 컨테이너다:

- 용량이 페이지와 다르다 (프로파일 값)
- 모든 페이지에서 동일하게 보인다
- 폴더를 담을 수 있다
- 위젯은 담을 수 없다 (타입으로 강제 가능한지 확인)

독을 "0번 페이지"처럼 취급하지 마라. 용량과 규칙이 달라서 특수 처리가 곳곳에 흩어지게 된다. 별도 컨테이너로 모델링하는 편이 결국 단순하다.

## 6. 프로파일 오류 감지

프로파일이 실제와 다르면 **추출 단계에서 즉시 드러난다.** 다음 신호를 감지하고 경보하라:

| 신호 | 의미 |
|------|------|
| 두 항목이 같은 슬롯으로 계산됨 | 행 또는 열 수가 실제보다 적다 |
| 항목이 격자 범위 밖 슬롯으로 계산됨 | 행 또는 열 수가 실제보다 적거나, 원점이 틀렸다 |
| 마지막 행/열이 항상 비어 있음 | 행 또는 열 수가 실제보다 많다 |
| 독 항목이 페이지 슬롯으로 계산됨 | 독 영역 경계가 틀렸다 |
| 아이콘 수와 인식된 슬롯 수가 다름 | 좌표 매핑 오류 또는 인식 누락 |

**첫 번째 신호가 가장 중요하다.** 슬롯 충돌은 프로파일 오류의 거의 확실한 증거이고, 이 상태로 계획을 세우면 아이콘이 잘못된 위치로 이동한다. 충돌을 감지하면 추출을 실패로 처리하고 실측 폴백으로 전환하라.

## 7. 프로파일 스키마 예시

```
DeviceProfile
  id                  : 프로파일 식별자
  deviceModel         : 기기 모델 (알 수 있는 경우)
  source              : "table" | "measured" | "estimated"
  verification        : "확인됨" | "문헌" | "미검증"

  page.rows           : 정수
  page.columns        : 정수
  page.maxPages       : 정수
  dock.capacity       : 정수
  folder.perPage      : 정수
  folder.maxPages     : 정수

  capabilities.allowsGaps        : bool   ← 계획 알고리즘을 가르는 플래그
  capabilities.widgetSizes       : 허용 크기 목록
  capabilities.dockAllowsFolder  : bool
  capabilities.dockAllowsWidget  : bool

  slotOrigin          : "topLeft"        ← 명시하지 않으면 모듈마다 달리 해석한다
  slotOrder           : "rowMajor"
```

`source`와 `verification`을 반드시 포함하라. 추정된 프로파일 위에서 동작할 때 상위 계층이 사용자에게 확인을 요청할 수 있어야 한다.
