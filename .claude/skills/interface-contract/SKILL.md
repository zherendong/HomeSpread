# Interface Contract — 모듈 경계의 합의

## 왜 계약이 필요한가

이 프로젝트의 네 모듈 — UI, 동기화 엔진, 레이아웃 모델, 기기 브리지 — 은 서로 다른 담당자가 병렬로 만든다. 각자 상대의 형식을 **상상하면서** 만들면, 그 상상의 차이는 코드가 다 완성된 뒤 통합할 때 드러난다.

더 나쁜 것은, 이 프로젝트에서 그 불일치가 **컴파일 오류가 아니라 사용자 홈화면의 손상**으로 나타난다는 점이다. 슬롯 인덱스의 원점을 한쪽은 좌상단, 다른 쪽은 좌하단으로 가정했다면, 아이콘은 아무 오류 없이 잘못된 곳으로 이동한다.

**계약은 문서 작업이 아니라 이 프로젝트의 안전장치다.**

## 계약 파일

경로: `_workspace/02_contracts/{name}.contract.md`

이 프로젝트의 핵심 계약:

| 파일 | 소유자 | 소비자 |
|------|--------|--------|
| `layout-model.contract.md` | homescreen-model-analyst | UI, 동기화 엔진, 기기 브리지 |
| `device-bridge.contract.md` | ios-protocol-specialist | 동기화 엔진, 추출 파이프라인 |
| `sync-engine.contract.md` | layout-sync-engineer | UI |
| `ui-viewmodel.contract.md` | ui-engineer | 동기화 엔진 (진행 이벤트 방향) |

**소유자는 한 명이다.** 두 명이 같은 계약을 고치면 계약의 목적이 사라진다.

## 계약 문서 형식

```markdown
# Contract: {이름}

**버전**: 1.0
**소유자**: {에이전트}
**소비자**: {에이전트 목록}
**최종 변경**: YYYY-MM-DD

## 목적

이 경계가 무엇을 나누는가. 한두 문장.

## 데이터 형식

### {타입 이름}
| 필드 | 타입 | 필수 | 의미 | 비고 |
|------|------|------|------|------|

(열거형은 가능한 값을 모두 나열한다)

## 호출 규약

### {연산 이름}
- 입력:
- 출력:
- 동기/비동기:
- 실패 시:
- 멱등성: 같은 입력으로 두 번 호출하면?

## 오류와 부분 실패

| 상황 | 표현 | 소비자가 해야 할 일 |
|------|------|-------------------|

## 이벤트 (비동기 진행이 있는 경우)

| 이벤트 | 언제 | 페이로드 |
|--------|------|---------|

## 불변식

이 계약을 통과하는 데이터가 항상 만족하는 조건.
(예: "slotIndex는 항상 프로파일의 격자 범위 안이다")

## 명시적 미정의

이 계약이 **의도적으로 정하지 않은 것**과 그 이유.

## 변경 이력

| 버전 | 날짜 | 변경 | 소비자 영향 |
|------|------|------|-----------|
```

## 반드시 명시해야 하는 것들

이 프로젝트에서 실제로 어긋나기 쉬운 지점들이다. 계약에 빠지면 통합 시점에 문제가 된다.

| 항목 | 왜 |
|------|-----|
| **슬롯 인덱스의 원점과 방향** | 좌상단/행 우선을 명시하지 않으면 모듈마다 달리 해석한다 |
| **좌표의 단위** | 논리 픽셀인가 물리 픽셀인가. DPI 배율이 적용된 값인가 |
| **페이지 인덱스의 시작** | 0부터인가 1부터인가 |
| **독의 표현** | 페이지 배열에 포함되는가, 별도 필드인가 |
| **부분 실패의 표현** | `completeness` 같은 필드로 명시. 예외로 던지면 부분 결과가 사라진다 |
| **시간 단위** | ms인가 s인가 |
| **비동기 이벤트의 순서 보장** | 순서가 보장되는가. 유실될 수 있는가 |
| **취소의 의미** | 즉시 중단인가, 현재 단계 완료 후 중단인가 |
| **선택 필드의 부재와 null의 차이** | "값 없음"과 "모름"이 다른 의미인가 |

## `Unknown`과 신뢰도는 계약에 들어간다

레이아웃 모델의 `Unknown` 타입과 `confidence` 필드는 내부 구현 세부가 아니라 **계약의 일부**다. 소비자가 이 값에 따라 동작을 바꿔야 하기 때문이다:

- UI는 낮은 신뢰도를 구분해 표시해야 한다
- 동기화 엔진은 낮은 신뢰도 항목을 계획에서 제외해야 한다

계약에 이 필드가 없으면 소비자는 이 구분을 할 수 없고, 결과적으로 인식하지 못한 아이콘을 밀어내게 된다.

## 변경 절차

1. **변경 필요를 감지하면 먼저 소유자에게 알린다.** 소비자가 임의로 자기 쪽만 바꾸면 불일치가 생긴다
2. 소유자가 계약을 수정하고 버전을 올린다
3. **모든 소비자에게 브로드캐스트한다.** 변경 이력에 "소비자 영향"을 반드시 채운다
4. 소비자는 영향 여부를 확인하고 응답한다
5. 응답이 모이기 전에는 변경된 계약 기반의 구현을 확정하지 않는다

### 버전 규칙

| 변경 | 버전 | 소비자 조치 |
|------|------|-----------|
| 선택 필드 추가 | minor | 없음 (무시 가능) |
| 필수 필드 추가 | major | 필수 |
| 필드 삭제·의미 변경 | major | 필수 |
| 열거형 값 추가 | major | 미지 값 처리 필요 |

**열거형 값 추가를 minor로 취급하지 마라.** 소비자가 모든 값을 열거해 처리하고 있다면, 새 값은 처리되지 않는 경로를 만든다.

## 계약 검증

계약이 지켜지는지 확인하는 것은 QA의 핵심 작업이다. 방법은 하나다: **생산자와 소비자의 코드를 동시에 열어 놓고 비교한다.**

| 확인 | 흔한 결함 |
|------|----------|
| 필드 이름 | 한쪽은 `slotIndex`, 다른 쪽은 `slot` |
| 타입 | 한쪽은 문자열, 다른 쪽은 숫자 |
| 필수 여부 | 생산자가 안 보내는 필드를 소비자가 필수로 읽음 |
| 열거형 값 | 소비자가 처리하지 않는 값을 생산자가 보냄 |
| 단위 | 한쪽은 ms, 다른 쪽은 s |
| 부분 실패 | 생산자는 `partial`을 보내는데 소비자가 무시하고 진행 |
| 이벤트 | 생산자가 발행하지 않는 이벤트를 UI가 기다림 |

**"계약 파일이 존재한다"는 검증이 아니다.** 계약과 양쪽 구현, 셋을 대조해야 검증이다.

## 계약을 먼저 쓰는 순서

설계 단계에서 계약을 **구현보다 먼저** 확정한다. 순서는:

1. 레이아웃 모델 계약 (다른 모든 것의 기반)
2. 기기 브리지 계약 (조사 결과가 나오는 대로)
3. 동기화 엔진 계약 (위 둘에 의존)
4. UI 뷰모델 계약 (위 셋에 의존)

1번이 흔들리면 나머지 셋이 전부 흔들린다. 그래서 레이아웃 모델 계약에 가장 많은 검토 시간을 쓴다.
