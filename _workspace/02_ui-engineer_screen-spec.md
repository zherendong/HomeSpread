# 화면 설계 — 여러 페이지를 한 화면에 펼치고 끌어 편집한다

**날짜:** 2026-08-20
**상태:** 구현 완료 · 실기기에서 편집→쓰기까지 확인됨 (2026-08-20)
**구현:** `src/ipsm/ui/`, `src/ipsm/app.py`, `run_app.bat`

## 이 화면이 존재하는 이유

iPhone 에서 홈화면을 정리하기 어려운 것은 **한 번에 한 페이지밖에 못 보기 때문**이다.
5페이지에 있는 앱을 2페이지로 옮기려면 아이콘을 붙잡은 채 화면 가장자리에서 기다려야 하고,
그동안 나머지 아이콘이 밀려 움직인다. PC 화면은 넓다. 그 넓이를 쓰는 것이 이 앱의 전부다.

**실시간 미러링이 아니다.** 읽어 와서 펼치고, PC 에서 편집하고, 확인한 뒤 한 번에 쓴다.

## 창의 구성

```
┌─ 도구모음: 기기에서 읽기 · 백업 파일 열기 · 아이콘 받기 │ 되돌리기 · 다시 실행 │
│            페이지 추가 │ 적용 · 백업으로 복원 │ 크기 [슬라이더] · 모두 보이게 ─┐
├──────────────────────────────────────────────────────┬───────────────────────┤
│  ┌1페이지 24/24┐ ┌2페이지┐ ┌3페이지┐ ┌4페이지┐ ┌5페이지┐ │ 미적용 변경 N건       │
│  │ ▣ ▣ ▣ ▣  │ │       │ │       │ │       │ │       │ │  (변경 목록)          │
│  │ ▣ ▣ ▣ ▣  │ │  ...  │ │  ...  │ │  ...  │ │  ...  │ │                       │
│  └───────────┘ └───────┘ └───────┘ └───────┘ └───────┘ │ 미배치 앱 N개         │
│  ┌6페이지 5/24┐                                        │  (되붙을 앱 목록)     │
│  │ ▣ ▣ ▢ ▢  │        (폴더를 열면 이 아래로 펼쳐진다) │                       │
│  └───────────┘                                        │ 도움말 두 줄          │
│                    ┌─ 독 4/4 ─┐                       │                       │
│                    │ ▣ ▣ ▣ ▣ │                       │                       │
├────────────────────┴──────────┴───────────────────────┴───────────────────────┤
│ 상태줄: 페이지 6장을 한 화면에 폈습니다.                                       │
└───────────────────────────────────────────────────────────────────────────────┘
```

- 페이지는 **흐름 배치(FlowLayout)** 로 창 너비에 맞춰 줄바꿈한다. 가로 스크롤을 두지
  않는 이유: 가로로 스크롤해야 보이는 페이지는 "한 화면에 펼쳤다"고 할 수 없다.
- **모두 보이게** 는 모든 페이지가 들어가는 가장 큰 타일 크기를 찾는다. 창이 작아
  들어가지 않으면 그 사실을 상태줄로 말한다 — 조용히 최소 크기로 주저앉지 않는다.

## 결정한 것과 그 이유

### 1. 한 페이지 = 위젯 하나

칸마다 위젯을 두지 않는다. 이 사용자의 홈화면만 해도 항목이 309개이고, 폴더를 펼치면 더
늘어난다. 위젯 300개를 만들면 창을 열 때부터 느리고, 배율을 바꿀 때마다 전부 다시 배치된다.
`ContainerView` 하나가 자기 칸 전부를 그린다 (REQ-012).

같은 위젯을 페이지·독·폴더 페이지에 모두 쓴다. 세 곳의 드롭 규칙이 서로 달라질 여지를
없애기 위해서다.

### 2. 옮길 수 있는가를 화면이 판단하지 않는다

`ContainerView` 는 아무것도 결정하지 않는다. 전부 `LayoutDocument.can_move()` 에 묻고,
거절 이유(한 문장)를 받아 상태줄에 그대로 띄운다.

판단이 두 곳에 있으면 반드시 갈린다. 갈리는 순간 사용자는 "놓을 수 있을 것처럼 보였는데
안 되는" 화면을 보게 되고, 그것은 앱이 고장 난 것으로 읽힌다.

거절은 **손을 놓기 전에** 알려야 한다. `dragMoveEvent` 에서 `event.ignore()` 를 부르면
커서가 '금지' 모양으로 바뀐다.

### 3. 폴더 안 / 폴더 옆을 한 동작으로

아이콘 한가운데 **62% 안**에 놓으면 폴더 안으로, 밖이면 폴더 옆자리로 들어간다.
드래그 중에는 어느 쪽으로 갈지 테두리로 그려 준다.

62% 라는 숫자에 이론적 근거는 없다. 다만 너무 크면 옆자리에 넣기 어렵고, 너무 작으면
폴더에 넣기 어렵다. 실제로 끌어 보고 조정할 값이다.

폴더가 가득 찼으면 **비어 있는 첫 폴더 페이지**를 찾아 넣는다. 전부 찼으면 거절한다.

### 3-1. 앱 위에 앱을 겹치면 새 묶음 (2026-08-20 추가)

폴더에 넣는 판정과 **같은 62% 안쪽 영역**을 쓴다. 대상이 폴더면 그 안으로, 대상이 앱이면
둘을 묶어 새 폴더를 만든다. 판정 영역을 하나로 둔 이유는 사용자가 이 둘을 다른 동작으로
생각하지 않기 때문이다 — iPhone 에서도 겹치는 손짓 하나다.

다만 **판이 스스로 문서를 바꾸지 않는다.** 묶기는 이름을 물어야 하는데, 그 창을 띄우기
전에 이미 묶여 있으면 취소를 눌러도 늦다. 그래서 `ContainerView` 는 `grouped(끌어온 uid,
놓인 uid)` 를 알리기만 하고, 이름을 묻고 `doc.group()` 을 부르는 일은 창이 한다.

### 3-2. 선택은 판이 아니라 창이 들고 있는다

여러 개를 골라 묶으려면 **페이지를 건너** 고를 수 있어야 한다. 판(`ContainerView`)이 저마다
선택을 들고 있으면 다른 페이지를 누르는 순간 앞의 선택이 사라진다. 그래서 선택 집합은
`MainWindow.selection` 하나뿐이고, 판은 그것을 받아 테두리를 그리기만 한다.

Ctrl 을 누른 채 누르면 더하거나 뺀다(`toggled`), 그냥 누르면 그것 하나만 남는다(`selected`).
다시 그릴 때마다 사라진 uid 는 조용히 뺀다 — 없는 것을 고른 채로 두면 '묶기'가 켜져 있는데
눌러도 아무 일이 없다.

### 4. 폴더는 새 창이 아니라 같은 창 아래쪽에

폴더 안팎으로 항목을 끌려면 **두 자리가 동시에 보여야 한다.** 새 창을 띄우면 뒤가 가려지고,
가려진 곳으로는 끌 수 없다.

### 5. 페이지 순서 바꾸기는 드래그가 아니라 버튼(◀ ▶)

드래그 체계를 둘로 만들면(아이콘을 끄는 것 / 페이지를 끄는 것) 지금 무엇이 잡혔는지
알기 어렵다. 페이지 순서는 자주 바꾸는 것이 아니므로 버튼이 낫다.

### 6. 다시 그리기는 항상 다음 차례로 미룬다

편집은 `ContainerView.dropEvent` 안에서 일어나고, 다시 그리기는 그 위젯의 부모를 새로 짓는다.
**드롭 처리 도중에 그 드롭을 받은 위젯을 지우면 앱이 죽는다.** 그래서 모든 `edited` 신호는
`QTimer.singleShot(0, …)` 를 거친다.

### 7. 아이콘은 받아 두고 다시 쓴다

앱 300개의 아이콘을 열 때마다 받으면 7초씩 기다린다. `iconModDate` 가 같으면 다시 받지
않는다. 웹 클립처럼 PNG 를 주지 않는 항목은 첫 글자를 딴 대체 타일로 그린다 — 못 받는 것이
정상인 항목이 있으므로, '실패'는 오류가 아니라 상태다.

## 적용 화면

순서는 **읽기 → 펼치기 → 편집 → 변경 목록 확인 → 백업 → 쓰기 → 결과 대조**.

적용 대화상자는 네 가지를 말하고, "위 내용을 확인했습니다"를 체크해야 버튼이 켜진다:

1. 적용 전 자동 백업하며, 백업이 실패하면 쓰지 않는다
2. 홈화면은 부분 수정이 아니라 전체가 한 번에 덮어써진다
3. 지금 홈화면에 없는 앱 N개가 마지막 페이지 끝에 붙는다 (이름을 최대 6개까지 나열).
   iOS 동작이라 **백업 복원으로도 되돌아가지 않는다**
4. 적용 중에 케이블을 뽑지 말 것

3번은 대화상자에서 처음 보면 늦다. 편집하는 내내 곁판의 **미배치 앱** 칸에 띄워 둔다.

**항등 검사를 통과하지 못한 홈화면은 적용 버튼 자체를 끈다.** 경고만 띄우고 버튼을 살려
두면, 경고를 닫은 사용자에게는 아무 일도 없었던 것과 같다.

## 실기기에서 편집하고 쓴 결과 (2026-08-20)

사용자가 직접 끌어 편집하고 두 번 적용했다.

| | 1차 | 2차 |
|---|---|---|
| 편집 | 카카오페이 스토어를 1페이지 폴더로 | 행아웃·라인을 1페이지 폴더로 |
| 손실 | 0 | 0 |
| iOS 가 덧붙인 것 | 0 | 0 |
| 보낸 것 vs 되읽은 것 | — | **완전 동일** |

'이동'으로 잡힌 나머지 항목은 전부 앞 칸이 비면서 뒤가 당겨진 것이다. 우리가 의도한
편집 외에 기기가 스스로 바꾼 것은 없었다.

**고친 것:** 도구모음 글씨가 보이지 않았다. 배경을 어둡게 칠하면서 `QToolButton` 의
글자색을 두지 않아 Windows 기본 팔레트의 **검정**이 어두운 배경에 얹혔다. 이제
스타일시트 맨 위에 `QWidget { color }` 를 하나 두어, 개별 규칙을 빠뜨려도 최소한
읽히게 했다.

## 묶기 · 이름 바꾸기 (2026-08-20)

| 확인한 것 | 결과 |
|-----------|------|
| 앱 위에 앱 겹쳐 놓기 | `grouped` 만 나가고 문서는 그대로 — 이름을 묻기 전에는 바뀌지 않는다 |
| 가장자리에 놓기 | 예전대로 옆자리에 끼운다 (묶기가 옆자리 놓기를 먹지 않았다) |
| 폴더 위에 놓기 | 예전대로 폴더 안으로 |
| Ctrl 로 페이지 건너 고르기 | 선택이 유지되고 묶기가 켜진다 |
| 묶은 뒤 되돌리기 | 원본과 완전히 동일 (`to_state() == origin`) |
| 이름 바꾸기 | `displayName` 한 키만 바뀌고 `iconLists` 는 그대로 |
| 이름 바꾸기 취소 | 문서가 바뀌지 않는다 |
| 이름만 바꿨을 때 | 아무것도 움직이지 않지만 `dirty` 가 참 — 적용 단추가 열린다 |

모두 화면 없는(offscreen) Qt 로 실제 창을 만들어 확인했다. `[미검증]` — 실기기에 묶기 결과를
써 보는 것은 아직 하지 않았다.

## 색은 짝으로만 정한다 (2026-08-20)

같은 실수가 두 번 났다.

| 언제 | 무엇을 빠뜨렸나 | 어떻게 보였나 |
|------|----------------|--------------|
| 도구모음 | 바탕만 어둡게 칠하고 글자색을 안 뒀다 | Windows 기본 검은 글씨가 어두운 바탕에 얹혀 안 보였다 |
| 이름 바꾸기 창 | `QWidget { color }` 로 글자만 밝게 칠하고 `QLineEdit` 바탕을 안 뒀다 | 기본 흰 바탕에 흰 글씨 |

방향만 반대일 뿐 원인은 하나다 — **바탕색과 글자색 중 하나만 정했다.** 그래서 규칙을
하나 둔다: 스타일시트에서 `color` 를 정하는 자리에서는 `background` 도 함께 정한다.
반대도 마찬가지다.

규칙을 눈으로 훑어서는 이 결함이 잡히지 않는다. `test_dialog_text_is_readable_on_its_own_background`
가 대화상자를 실제로 그린 뒤, 위젯 자리를 잘라 바탕과 가장 먼 색의 밝기 차를 잰다.
차이가 80 미만이면 떨어진다.

## 남은 것 `[미검증]`

- HiDPI 200% 배율
- 위젯이 있는 홈화면에서 '알 수 없는 항목' 타일이 어떻게 보이는가
