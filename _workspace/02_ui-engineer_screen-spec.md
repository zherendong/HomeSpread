# 界面规格——同时展开多个页面并拖动整理

**原始日期：**2026-08-20。**校订日期：**2026-11-13。

**历史状态：**上游已实现，并于 2026-08-20 在注明的实机上完成编辑到写入验证。

**实现：**`src/ipsm/ui/`、`src/ipsm/app.py`；原 Windows 入口为 `run_app.bat`，macOS 使用独立启动脚本和 `.app`。

上游的实机结果不代表当前 Mac 所连手机已经通过写入验证。当前验收见 `04_macos-qa_final-report.md`。

## 界面目的

iPhone 一次只能查看一个主屏幕页面。将第 5 页应用移到第 2 页时，用户需要拖住图标并等待翻页，其它图标还会随之移动。应用利用电脑屏幕同时展示页面，让整理过程可见。

工作方式是读取布局、在电脑上编辑、核对改动后一次提交；没有实时镜像或遥控手机屏幕。

## 窗口组成

```text
┌─ 工具栏：从设备读取 · 打开备份 · 获取图标 │ 撤销 · 重做 │ 新增页面 ──────┐
│           写入兼容性测试 · 应用 · 从备份恢复 │ 大小 [滑块] · 全部显示       │
├───────────────────────────────────────────┬─────────────────────────────┤
│ ┌第1页 24/24┐ ┌第2页┐ ┌第3页┐ ┌第4页┐    │ 未应用更改 N 项              │
│ │ ▣ ▣ ▣ ▣  │ │     │ │     │ │     │    │ （更改列表）                 │
│ │ ▣ ▣ ▣ ▣  │ │ …   │ │ …   │ │ …   │    │                              │
│ └───────────┘ └─────┘ └─────┘ └─────┘    │ 未放到桌面的应用 N 个         │
│ ┌第5页──────┐ ┌第6页 5/24┐                 │ （可能被系统放回的应用）      │
│ │ …         │ │ ▣ ▣ ▢ ▢ │                 │                              │
│ └───────────┘ └──────────┘                 │ 两行操作提示                 │
│       （打开文件夹时，在下方展开内容）      │                              │
│              ┌─ 程序坞 4/4 ─┐             │                              │
│              │  ▣ ▣ ▣ ▣    │             │                              │
├──────────────┴──────────────┴─────────────┴─────────────────────────────┤
│ 状态栏：已在同一画面展开 6 页。                                           │
└─────────────────────────────────────────────────────────────────────────┘
```

- 页面采用 `FlowLayout`，随窗口宽度换行，避免依靠横向滚动才能看到其它页面。
- “全部显示”寻找能容纳全部页面的最大图标块尺寸；窗口过小时明确提示，而不是静默缩到难以阅读的大小。垂直空间不足时仍可滚动。

## 设计决定

### 1. 每个页面使用一个绘制控件

不为每一格创建独立控件。上游样本已有 309 个条目，展开文件夹后可见项更多；大量控件会增加创建和缩放重排成本。一个 `ContainerView` 绘制自身全部格子（REQ-012）。

页面、程序坞和文件夹内页共用该控件，避免出现三套不同的拖放判定。

### 2. 合法移动由模型判断

`ContainerView` 向 `LayoutDocument.can_move()` 询问移动是否合法，把模型返回的一句话原因显示在状态栏。界面不复制模型规则，否则容易出现“看起来可以放，松手却失败”的不一致。

拒绝应在松手前可见：`dragMoveEvent` 调用 `event.ignore()`，使鼠标显示禁止指针。写入入口还会执行独立的原始条目和未知项位置校验。

### 3. 同一次拖动区分文件夹内部与旁边

落点位于图标中央 **62% 区域**时进入文件夹，落在边缘时插入旁边；拖动中用边框显示目标含义。

62% 是交互参数，不是理论结论。区域过大会妨碍插入旁边，过小会妨碍放入文件夹；只有实际交互证据表明需要调整时才修改。

目标文件夹的当前页已满时，由模型寻找可用页或在页数限制内新增页；达到整个文件夹容量限制才拒绝。原设计中“所有现有页都满就拒绝”的描述已被后续扩页实现取代。

### 3.1 应用叠放创建文件夹

2026-08-20 增加。使用同一个中央 62% 判定区域：目标是文件夹则移入，目标是应用则将两者组成新文件夹。这与手机上叠放图标的动作一致。

画布本身不修改文档。创建文件夹前需要询问名称，如果先分组再弹窗，取消就失去意义。因此 `ContainerView` 只发出 `grouped(拖动项 uid, 目标项 uid)`，由主窗口询问名称后调用 `doc.group()`。

### 3.2 主窗口统一保存选择集

跨页多选要求选择状态不归单页控件所有。唯一选择集是 `MainWindow.selection`，各 `ContainerView` 只按它绘制边框。

Windows 按住 Ctrl 点击可增加或移除选择（`toggled`）；macOS 对应 Command。普通点击只保留单项（`selected`）。重绘时移除已经不存在的 uid，避免“分组”按钮启用却没有有效目标。

### 4. 文件夹在同一窗口下方展开

跨文件夹内外拖动时，来源和目标需要同时可见。另开窗口会遮住页面，所以文件夹内容在原窗口下方展示。

### 5. 页面排序使用按钮

使用 `◀`、`▶` 按钮移动页面顺序。图标拖动和页面拖动若共用画布，容易使用户不清楚当前拖动对象；页面排序频率较低，按钮能清楚表达操作。

### 6. 重绘推迟到下一次事件循环

编辑发生在 `ContainerView.dropEvent` 中，而完整重绘会重建其父控件。处理拖放时删除正在处理事件的控件会崩溃，因此 `edited` 信号后的刷新通过 `QTimer.singleShot(0, …)` 调度。

### 7. 缓存图标

原上游约 300 个图标每次重新获取需要约 7 秒。`iconModDate` 未变化时复用本地缓存；网页快捷方式等不提供 PNG 的条目显示首字符替代块。无法取得这类图标是可展示状态，不应阻断编辑。

## 兼容性测试与应用确认

普通流程为：**读取 → 展开 → 明确确认的原样回写兼容性测试 → 编辑 → 查看变更 → 再次确认 → 备份 → 写入 → 结果比较**。

兼容性测试本身是一次真实写入，可能触发 App 资源库回填。只允许对未编辑的当前设备布局发起；普通读取不自动运行它。`verify_identity()` 只验证内存解析/重建是否保真，不能替代实际设备兼容性测试。

应用确认框说明以下内容，勾选“我已了解上述内容”后才启用执行按钮：

1. 写入前自动备份，备份失败即停止。
2. 操作会替换整份主屏幕布局。
3. 尚未放在桌面的应用可能被系统放回最后一页；展示数量及最多六个名称。**恢复备份也不能撤销这项副作用。**安装清单查询失败时，不把空清单当成绝不会回填的保证。
4. 操作期间保持数据线连接和手机解锁。

可能回填的应用在编辑侧栏持续显示，不能直到确认框才第一次告知。

普通编辑的“应用”同时要求：内存保真检查通过、本次会话 `write_verified` 为真、有更改、来源是真实设备且没有其它任务。原样回写测试成功，或明确确认的恢复成功且读回比较安全，均可建立或刷新该标记。加载或失败后标记失效；界面与工作线程都检查。

**从备份恢复是独立恢复入口。**即使兼容性测试失败，也允许用户明确确认后恢复同设备的有效备份，避免无法使用写入前备份。恢复仍执行归属和完整性校验、恢复前备份、写后比较，并提示未验证/失败状态的额外风险；绝不自动恢复。

## 背景色和文字色成对设置

2026-08-20 出现过两次同类错误：

| 位置 | 遗漏 | 表现 |
|------|----------------|--------------|
| 工具栏 | 只设深色背景，未设文字色 | Windows 默认黑字叠在深色背景上 |
| 重命名对话框 | `QWidget { color }` 只设浅色文字，`QLineEdit` 未设背景 | 默认白底白字 |

根因相同：只指定了背景色或文字色中的一项。因此设置 `color` 时同时设置 `background`，反向也适用。

`test_dialog_text_is_readable_on_its_own_background` 实际渲染对话框，截取控件区域，计算背景与最远颜色的亮度差；差值低于 80 时失败。仅阅读样式表不能替代渲染验证。
